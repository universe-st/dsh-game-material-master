## 0. 摘要

### 0.1 一句话结论

这个模块的工程难点**不在调用模型，而在几何**。研究阶段的结论非常明确：
把"画对形状"从 AI 手里拿走之后，几何问题就从一个概率问题变成一个确定性问题。
所以开发计划的主线是 **先做一个纯计算、可独立测试的几何内核（M0），再往上搭数据和界面**。

### 0.2 三个必须先立的工程原则

| # | 原则 | 违反后果（已实测） |
|---|---|---|
| **P1** | 几何量必须**从图里量**，不允许硬编码任何尺寸 | 一次把上游图从 2048 缩到 1536，硬编码的模板几何失效，地块被裁出透明缺口、拼图能看见网格线，**而且不报任何错** |
| **P2** | 规整（量 → 对齐 → 裁）**不可跳过** | 只有模板不规整 → 每张位置都不同，拼图错位；"模板填充 + 规整"是双保险，缺一不可 |
| **P3** | **不允许用 AI 生成菱形模板** | 参考图引导的自由生成达标率 0%（比例 1.41~1.92）。这是整个模块可靠性的根基 |

### 0.3 四个关键数字（对齐验收）

来自研究报告的实测，是设计目标也是回归断言：

| 指标 | 实测值 | 断言阈值 |
|---|---|---|
| 规整后菱形比例 | 9 张地块 `1.986 ~ 2.019` | `\|ratio − 2\| ≤ 0.05` |
| 菱形边缘直线度（2048² 源图） | 残差 `1.5 ~ 2.0 px` | `≤ 3 px` |
| 同类地块铺 5×5 的透明缺口 | **0** | `= 0` |
| 装饰底部锚点（草地，64×96 单元格） | 地面线在 `53.5` | `54 ± 2` |

## 1. 研究阶段已经验证过什么

这一节是给实现者的"已确认事实"清单。**这些不是待验证的假设，是实现时必须照做的约束。**

### 1.1 已确立的算法路径

```
① 模板渲染（本地，纯计算）
   洋红 #FF00FF 实心 2:1 菱形，超采样 4× 后降采样
   → probe/tpl/t1-2048.png（单格）、t2x2-2048.png（2×2 地基）

② 生成（Seedream）
   地形地块：模板填充（input image = 模板）
   独立装饰：白底单图（无模板）
   大型建筑：2×2 地基网格模板

③ 规整（本地，纯计算）
   抠底（alpha 优先 / 边框众数色泛洪）→ 剔除洋红残留
   → 只量下半部分两条下边（稳健直线拟合）→ 求下顶点与左右顶点
   → 仿射变换到标准菱形 → 按数学菱形裁 alpha

④ 拼图（本地，纯计算）
   步进 (±tw/2, +th/2) 就是 (±32, +16)；按 (r+c) 升序绘制；
   装饰作为独立图层插在"自己那格之后、前排之前"；
   每类地形按类别随机抽变体
```

### 1.2 研究期踩过、实现时必须避开的坑

| # | 坑 | 症状 | 对策 |
|---|---|---|---|
| K1 | 硬编码模板几何 | 地块被裁出透明缺口，拼图见网格线，**不报错** | `template_diamond()` 从模板图实测 |
| K2 | 背景判定用"离背景色远 = 前景" | 草地地块整张画布被当前景，拟合斜率毫无意义（实测 1.14） | 改成"从四边泛洪"，只把与边框连通的近似背景色算背景 |
| K3 | 网格步进当成贴图尺寸 | 64×64 按 64 步进铺，整张图裂成白格 | 步进是贴图尺寸的 `(1/2, 1/4)` |
| K4 | 同一张图里"地面 + 装饰"按 y 切层 | **装饰被画两遍**（地面层半棵 + 装饰层整棵） | 分两次生成 |
| K5 | `np.where` 返回 `(行, 列)` 当成 `(x, y)` | 缩放系数变成负数，产出垃圾图，**不报错** | JS 里没有这个问题，但端口时要保持"先取 xMin/xMax 再取 yMin/yMax"的可读写法 |
| K6 | `background:"transparent"` 假定一定成功 | 4.0 忽略它输出 JPEG；5.0 Lite 时灵时不灵 | 按**实际 alpha 通道**判断，不假定请求成功 |
| K7 | 装饰锚点取菱形下顶点 | 树干插到地块前沿之外 | 锚点 = 地面上"站得住"的高度（实测 54） |
| K8 | 装饰不统一尺度 | 一棵树巨大、一棵很小，树干粗细不一 | 宽度归一化到 40px（≈ 菱形宽的 5/8）+ 高度上限 |
| **K9** | **抠完底又做不感知 alpha 的缩放** | 装饰边缘一圈**白描边**；成品 alpha 只剩 `{0,255}` 两个值（无抗锯齿） | 软 alpha + 只用可信像素颜色（最近邻填充）+ **颜色与 alpha 分开缩放** |
| **K10** | **软 alpha 的映射没有死区** | 纯白底图的压缩噪声（`dist`≈2~10）被判成 α≈0.03 的前景，背景色被抹到边缘，**白边反而更严重**（实测边缘 35% 洗白） | 加死区 `lo=40`；`dist` 低于它一律当背景 |
| **K11** | 对「上千源像素平均出来的颜色」做 unmatte | `F=(C−(1−α)B)/α` 几乎不改变颜色（C̄ 不是单个已合成像素），且 α→0 时数值不稳 | 不用 unmatte，改用"最近可信邻居的颜色填充" |

> K9/K10/K11 的完整排查过程与数据见 `research/REPORT.md` §8.7。三条都是**静默错误**：
> 不报错、不崩溃，只是画面上多一圈白描边。所以 §10.2 的 D5~D8 是必须写的回归断言。

> 详细机理与数据见 `research/REPORT.md` 的第三章、第八章、第十一章。

## 2. 目标、成功判据与非目标

### 2.1 目标

把研究阶段验证过的 Python 算法**原样移植**到插件的宿主半区（TypeScript，零外部依赖），
并接上数据层、服务层、对话调用面与界面，形成与现有四个模块同构的第五个模块。

### 2.2 成功判据（可度量）

| # | 判据 | 阈值 |
|---|---|---|
| A1 | 规整后地块菱形比例 | `\|ratio − 2.0\| ≤ 0.05`，**100% 达标** |
| A2 | 菱形边缘直线度（2048² 源图） | 残差 `≤ 3 px` |
| A3 | 菱形内无透明缺口 | 缺口像素数 `= 0` |
| A4 | 菱形外无非透明像素 | 越界像素数 `= 0` |
| A5 | 同类地块铺 5×5 无缝 | 整体 alpha 的"洞" `= 0` |
| A6 | 同种子 + 同布局 → 逐像素一致 | 两次渲染 `Buffer.equals` 为真 |
| A7 | 装饰底部锚点 | 树干底端落在 `54 ± 2` |
| A8 | 离线自检全绿 | 新增 `verify-tile.mjs` ≥ 60 项断言全过，且含 ≥ 1 条反向验证 |
| A9 | 端到端可跑通 | Playwright 真机：新建 → 模板 → 生成 → 验收 → 拼图 → 导出，无刷新页面 |

### 2.3 非目标

与产品文档 §九 一致，开发上额外明确两条：

| # | 不做 | 原因 |
|---|---|---|
| N-A | 不引入任何运行时依赖（含图像库） | 仓库硬约束。PNG 解码用 ffmpeg（既有做法），编码用 `src/png.ts`；几何计算手写 |
| N-B | 不把 Python 工具链带进插件 | `research/tools/` 只作为"参考实现 + 可复跑验证"，插件里是独立的 TS 实现，两者用同一批 fixture 对照 |

## 3. 总体架构

### 3.1 分层

```
┌─ 界面层（浏览器半区 · src/client.ts） ──────────────────────────────┐
│  TilePanel：步骤条 ①项目 ②模板 ③生成 ④验收 ⑤拼图                   │

└──────────────────────────┬──────────────────────────────────────────┘
                           │ Typert wire（每个方法一个 payload 对象）
┌──────────────────────────▼──────────────────────────────────────────┐
│  服务层（宿主 · src/index.ts 的 GameStudioGateway）                  │
│  tile 分支：13 个远程方法                                           │
└──────────────────────────┬──────────────────────────────────────────┘
┌──────────────────────────▼──────────────────────────────────────────┐
│  流水线层（src/tilegen.ts）                                         │
│  TileProject 状态机 · 阶段失效传播 · 作业与进度 · 审核模式            │
└──────┬────────────────────────────────────┬─────────────────────────┘
       │                                    │
┌──────▼──────────────┐          ┌──────────▼──────────────────────────┐
│ 几何内核（纯计算）   │          │ 生成适配层                          │
│ tilegeom.ts         │          │ ark.ts 的 generateImage()（复用）    │
│  · 模板渲染          │          │ 提示词构造（tileprompt 内联在 gen）  │
│  · 抠底 / 剔残留     │          └──────────┬──────────────────────────┘
│  · 菱形测量          │                     │
│  · 仿射规整          │          ┌──────────▼──────────────────────────┐
│ tilemap.ts          │          │ 落盘 / 资源路由                     │
│  · 变体随机          │          │ store.ts 的 tile 分区 + SERVABLE_DIRS│
│  · 等距拼图          │          └─────────────────────────────────────┘
│  · 跨格贴图锚点      │
└─────────────────────┘
```

**为什么几何内核单独成文件**：它是唯一有真实算法复杂度、且能脱离网络与 DSH 单独测试的部分。
研究期已经用 Python 验证过算法，移植后要能用同一批 fixture 逐位对齐。

### 3.2 五阶段流水线

| 阶段 | key | 花钱 | 产物 |
|---|---|---|---|
| ① 模板 | `template` | ❌ | `template/cell.png`（单格）、`template/grid2x2.png`（2×2 地基） |
| ② 生成 | `generate` | ✅ | `raw/<key>.v<N>.png`（原始生成）、`cell/<key>.v<N>.png`（规整后）、`decor/<key>.png` |
| ③ 验收 | `review` | ❌ | 每项的 `approved` 标记 |
| ④ 拼图 | `map` | ❌ | `map/map.png`、`map/map.json` |
| ⑤ 导出 | `export` | ❌ | `export/tiles/*.png`、`export/map.png`、`export/map.json` |

失效传播（沿用 `riggen.ts` 的 `invalidateFrom` 思路）：

```
改画风 / 改内容描述 / 改变体数  → 作废 ②③④⑤（②要重花钱）
生成模板（几何变化）           → 作废 ②③④⑤（②要重花钱）
单个变体重跑                   → 只作废该项的 ③
打 / 取消通过                  → 不作废任何东西
改布局 / 换种子 / 手动编辑      → 只作废 ④⑤（免费，随时可重做）
```

> **注意**：模板几何变化必须作废②。这是"几何唯一真源"的直接后果 ——
> 研究期正是这里出过一次静默错误（K1）。

### 3.3 磁盘布局

```
$DSH_HOME/game-material-master/tiles/<projectId>/
  project.json                  # TileProject（唯一状态文件）
  template/
    cell.png                    # 单格洋红菱形（2048²）
    grid2x2.png                 # 2×2 地基网格
  raw/                          # 原始生成结果（保留，便于回溯与重规整）
    grass.v1.png
    tree.v1.png
    building.v1.png
  cell/                         # 规整后的单元格地块（64×96 ... 按项目设置）
    grass.v1.png
    grass.v2.png
    bush.v1.png
  decor/                        # 独立装饰图层
    tree.png
    tree4.png
    boulder.png
  map/
    map.png
    map.json
  export/
    map.png
    map.json
    tiles/*.png
  logs.json                     # 与现有模块同构的操作日志
```

**为什么要同时留 `raw/` 和 `cell/`**：
规整参数（比如单元格尺寸）改了以后，可以**零成本**从 `raw/` 重新规整一遍，
不必重新花钱生成。这是模块里最实用的一条降本设计。

## 4. 数据模型

### 4.1 `TileProject`

```ts
/** 项目级设置：整份地图的几何规格。改动会作废下游。 */
interface TileSettings {
  /** 单元格宽（默认 64）。必须能被 4 整除 —— 菱形半宽要落在整数格上。 */
  cellWidth: number;
  /** 单元格高（默认 96）。菱形占中部 32px，上方留 32px 给高出地面的装饰。 */
  cellHeight: number;
  /** 菱形宽高比。恒为 2。**写死不给改** —— 改了就不是等距了。 */
  diamondRatio: 2;
}

/** 一个地块条目（一类地形 / 一个装饰 / 一栋建筑）。 */
interface TileItem {
  /** 稳定 key，也用作文件名（草 grass / 树 tree / 建筑 building）。 */
  key: string;
  /** 界面显示名（中文原文，走 T()）。 */
  label: string;
  kind: "terrain" | "decor" | "building";
  /** 同类变体分组：铺图时按这个分组随机抽。单变体时等于自己的 key。 */
  family: string;
  /** 占格 [列数, 行数]。地形与装饰是 [1,1]，建筑是 [2,2]。 */
  footprint: [number, number];
  /** AI 只描述「菱形里面是什么」。不描述形状 / 角度 / 透视。 */
  content: string;
  /** 生成方式。terrain → template；decor → plain；building → grid2x2。 */
  mode: "template" | "plain" | "grid2x2";
  /** 要几个变体（1~6）。 */
  variantCount: number;
  /** 已生成的变体。 */
  variants: TileVariant[];
  /** 单项通过标记；变体级通过标记在 TileVariant 里。 */
  approved?: boolean;
}

interface TileVariant {
  /** 0 起的变体下标；文件名用 v1/v2/…（1 起）。 */
  index: number;
  /** 相对项目目录的原始生成图路径。 */
  raw: string;
  /** 相对项目目录的规整产物路径。 */
  cell: string;
  /** 规整报告。 */
  report: TileGeomReport;
  approved?: boolean;
  /** 失败原因（有值表示这一张没成）。 */
  error?: string;
}

/** 规整报告：界面用它算状态角标，回归测试用它做断言。 */
interface TileGeomReport {
  /** "measured" = 量测成功；"template" = 测量失败回退到模板几何。 */
  mode: "measured" | "template";
  /** 实测菱形比例（宽/高）。理想 2.0。回退时无此值。 */
  ratioMeasured?: number;
  /** 两条下边的最大拟合残差（源图像素）。 */
  edgeResid?: number;
  /** 实测菱形半宽 / 半高。 */
  w2?: number;
  h2?: number;
  /** 缩放系数 [sx, sy]。 */
  scale: [number, number];
  /** 被剔掉的洋红残留像素数。 */
  magentaPurged?: number;
  /** decor 专用：装饰在源图里的 bbox 与在单元格里的尺寸 / 位置。 */
  decorBBox?: [number, number, number, number];
  decorSize?: [number, number];
  decorAt?: [number, number];
  /** 是否自动重跑过一次（F3.4）。 */
  retried?: boolean;
}

/** 拼图状态。布局与几何分离，所以改布局零成本。 */
interface TileMapState {
  rows: number;
  cols: number;
  /** 随机种子（变体抽取用它）。同种子 + 同布局 = 逐像素一致。 */
  seed: number;
  /** 每格的地形类别 key。空串 = 空格。 */
  cells: string[][];
  /** 独立装饰：{ "r,c": decorKey }。 */
  decor: Record<string, string>;
  /** 跨格建筑锚点：[r, c, key]。 */
  buildings: Array<[number, number, string]>;
  /** 产物路径。 */
  png?: string;
  json?: string;
}
```

### 4.3 作业与进度

复用 `pipeline.ts` 的作业模型（`JobInfo` + 单飞 + 取消），但**不复用它的实现**（那个是 sprite 专用的）。
tilegen 自己维护一份轻量的作业表：

```ts
interface TileJob {
  projectId: string;
  kind: "template" | "generate" | "map" | "export";
  /** 本次作业要覆盖的目标集合 —— 界面遮罩必须按它盖住"还没轮到"的项。 */
  targets: string[];           // 形如 "grass" / "grass#v1"
  done: string[];
  running: string | null;
  startedAt: number;
  error?: string;
}
```

> **`targets` 是硬要求**：不盖遮罩时界面看着完全正常，只是"点了没反应"，
> 用户会反复点，而每次点击都真实计费。现有模块的 `verify-feedback.mjs` 会拦这类问题，
> tile 也要进同一套检查。

## 5. 几何内核规格（M0 的核心）

这是全模块唯一有算法复杂度的部分。所有函数**纯计算、无 IO、可单测**。

### 5.1 `renderDiamondTemplate(opts)`

```ts
function renderDiamondTemplate(opts: {
  size: number;                 // 画布边长（默认 2048）
  cols: number;                 // 1（单格）或 2（2×2 地基）
  rows: number;
  margin?: number;              // 默认 0.92
  color?: [number, number, number];  // 默认 [255, 0, 255]
  ss?: number;                  // 超采样倍数，默认 4
}): { rgba: Buffer; width: number; height: number; geom: TemplateGeom };
```

要点：

1. **手写扫描线填菱形**（不引依赖）。给定菱形四顶点，逐行算 x 区间填色。
2. **超采样**：先在 `size*ss` 上填，再用 box filter 降到 `size`，边缘干净。
3. **返回 `geom`**（菱形的 bbox 与中心）。**这是 P1 的落点** ——
   模板刚渲染完就知道几何，不必事后去量；但下游仍然要重新量一次（P2 双保险）。
4. 2×2 地基额外画：洋红外框（大菱形轮廓，线宽 ≈ `tw*0.006`）+ 红色分格线（4 个子菱形边）。
   分格线是给**模型看的**，让它理解"这是 4 格"。

**为什么 `margin=0.92`**：研究期实测这个比例下模型既不会把菱形画出画布，也不会画得太小。
太小会更容易残留模板底色。

### 5.2 `measureGroundDiamond(rgba, w, h)`

```ts
function measureGroundDiamond(rgba: Buffer, w: number, h: number): GroundMeasure;
interface GroundMeasure {
  /** 实测菱形半宽 / 半高（源图像素）。 */
  w2: number; h2: number;
  /** 下顶点。 */
  xBot: number; yBot: number;
  /** 左 / 右顶点。 */
  xL: number; xR: number;
  /** 两条下边的最大拟合残差。 */
  resid: number;
  /** 实测比例。 */
  ratio: number;
}
```

算法（必须在注释里写清"为什么")：

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 1 | 求前景掩码 | alpha 有效（`min(alpha) < 24`）就信 alpha；否则取**边框众数色**，从**四边泛洪**标背景 | "离背景色远 = 前景"在草地上会全图误判（K2） |
| 2 | 取紧致包围盒 | 只用于定扫描范围 | |
| 3 | 从下往上扫**下半部分**（`t + 0.5H` 起） | 每行取最左 / 最右前景像素，跳过宽度 < 8 的行 | 装饰在上方会污染拟合；尖端行噪声大 |
| 4 | 对左右两条边界各做**稳健直线拟合** | 最小二乘 + 按残差裁剪，迭代 4 次；残差阈值 `max(2, p80)` | 偶发的装饰外溢像素会拉偏普通最小二乘 |
| 5 | 两线交点 = 下顶点；左边界 x 最小处 = 左顶点；右边界 x 最大处 = 右顶点 | | |
| 6 | `w2 = xBot − xL`，`h2 = yBot − yL`，`ratio = w2/h2` | 用**同一条下边**上的两个端点算，比用包围盒稳 | 装饰会撑大包围盒 |

**可信度判定**（供自动重跑用）：

```ts
/** 前景占比 > 0.75（说明没抠出背景）或 h2 > H*0.4（说明量到了装饰）→ 判定不可信。 */
```

### 5.3 `regularizeToCell(raw, measure, settings)`

```ts
function regularizeToCell(
  raw: { rgba: Buffer; w: number; h: number },
  m: GroundMeasure | null,      // null → 回退模板几何
  s: TileSettings
): { rgba: Buffer; w: number; h: number; report: TileGeomReport };
```

步骤：

1. 目标菱形四顶点（**固定位置，由 `settings` 算出**）：

   ```
   记 cellW = s.cellWidth, cellH = s.cellHeight, dw = cellW, dh = cellW / 2   // 2:1 等距
   菱形中心 cy = cellH / 2
   上 (cellW/2, cy − dh/2)   右 (cellW, cy)   下 (cellW/2, cy + dh/2)   左 (0, cy)
   ```

   以 64×96 为例：`dw=64, dh=32, cy=48` → 上 `(32,32)` 右 `(64,48)` 下 `(32,64)` 左 `(0,48)`。
   可见 `cellH=96` 给出的上方留白是 `cy − dh/2 = 32` px —— 正好是给高出地面装饰的空间。
   **`cellH` 只影响留白，不影响菱形尺寸**（菱形尺寸完全由 `cellW` 决定）。
2. 仿射变换（双线性重采样），把实测菱形映射到目标菱形。
3. 按**数学菱形**裁 alpha：`|x+0.5−cx|/(dw/2) + |y+0.5−cy|/(dh/2) <= 1` 保留，其余 `alpha=0`。
   边界带 0.7px 羽化，避免硬边锯齿。
4. 剔洋红残留：`|rgb − (255,0,255)| < 60` 的像素 `alpha=0`。
5. 出报告。

> **第 3 步是 A3/A4 两条断言的唯一实现点**，也是"拼图能看见网格线"的根因所在（K1）。
> 测试必须专门覆盖。

### 5.4 `regularizeDecorSprite(raw, settings)`

独立装饰（树、巨石）专用，与 5.3 不同：

1. 前景 bbox（白底抠除：边框众数色 + 泛洪）。
2. 定锚点 `anchorY`（装饰底部落在哪一行）：

   ```
   // 地面上"站得住"的高度 = 菱形下顶点 再往上半个下边的高差
   //   菱形下顶点 y  = cy + dh/2 = cellH/2 + cellW/4      （64×96 → 48 + 16 = 64）
   //   菱形中轴处的地面线比下顶点高 dh/4 = cellW/8        （2:1 菱形的几何性质，64×96 → 8）
   //   再扣 2px 抗锯齿与实测误差
   anchorY = cellH/2 + cellW/4 − cellW/8 − 2              （64×96 → 64 − 8 − 2 = 54）
   ```

3. 缩放：`k = min(40 / w, anchorY / h)`。
   - `40` ≈ 菱形宽的 5/8 —— **统一世界尺度**，所有装饰用同一个宽度（K8）。
   - `anchorY` 是高度上限，保证装饰不超出单元格顶部。
4. 摆位：水平居中，底部对齐 `anchorY`。

> **`anchorY` 必须由 `settings` 推导，不能写死 54。**
> 研究期这个值是从草地上量出来的：草坪地块在菱形中轴 `x=32` 处，
> 不透明像素 y 范围是 `40.0 .. 53.5`。上面公式给出的 54 与实测一致（差 0.5px）。
>
> **不要**把锚点取成菱形中心（48，树会浮空）或菱形下顶点（64，树干会插到地块前沿之外）。
> 这两个错误都在研究期实际出现过。

### 5.5 `assembleMap(tiles, mapState, settings)`

```ts
function assembleMap(
  lookup: Map<string, { rgba: Buffer; w: number; h: number }>,
  state: TileMapState,
  settings: TileSettings,
  opts: { background?: [number, number, number, number]; scale?: number }
): { rgba: Buffer; w: number; h: number };
```

要点：

1. **步进**：`stepX = cellW / 2`，`stepY = 菱形高 / 2`。

   > ⚠️ **这里是最容易写错的一处。** 菱形高不等于 `cellH`：
   > 菱形高由**宽**决定（2:1 等距 ⇒ `diamondH = cellW / 2`），`cellH` 只是"单元格"的高度，
   > 它比菱形高多出来的部分是留给高出地面的装饰的。
   >
   > ```
   > 默认 64×96：  diamondW = 64, diamondH = 32
   >                  stepX = 64/2 = 32
   >                  stepY = 32/2 = 16   ← 来自 diamondH，不是 cellH
   > 错误写法：      stepY = cellH/4 = 24   → 整张图裂开
   > ```
   >
   > 实现时必须写成 `const stepY = (cellW / 2) / 2`，并在注释里点明"来自菱形高，不是单元格高"。
   > 研究期第一次拼图就是因为把贴图尺寸当成了步进，整张图裂成白格（K3）。

2. **格 (r,c) 的位置**：`x = originX + (c−r)·stepX`，`y = originY + (c+r)·stepY`。
   （64×96 下就是 `(±32, +16)`。）
3. **绘制顺序**：按 `(r+c)` 升序。同 `(r+c)` 时按 `r` 升序。
4. **装饰**：插在"自己那格画完之后、下一格之前"。因为前排格的菱形下边会压住它的底部，
   所以**不需要额外 z 排序**。
5. **跨格建筑**：大菱形下顶点锚到 2×2 区域右下格的菱形下顶点。
   位置 = `originX + (c−r)·stepX − w/2`，`y = originY + (r+c+2)·stepY − (h − 8·scale)`。
6. **变体抽取**：`mulberry32(seed + r * cols + c)` 之类的确定性 PRNG（**不能用 `Math.random`**，
   否则违反 A6）。
7. **画布尺寸守卫**：`W = (cols+rows)·stepX + cellW`，`H = (rows+cols)·stepY + cellH·2`；
   `> 8192` 时拒绝并给明确错误。

### 5.6 PNG 编解码

- **编码**：复用 `src/png.ts` 的 `encodePng(rgba, w, h)`，够用。
- **解码**：**需要新增**。现有代码全靠 ffmpeg 解码（视频抽帧）。
  两个选择：
  - (a) 也走 ffmpeg：`ffmpeg -i in.png -f rawvideo -pix_fmt rgba -` 读回。**推荐**，
    零新代码、久经考验、仓库既有依赖；
  - (b) 手写 PNG 解码器（zlib inflate 有现成的 `node:zlib`）。
    PNG 的 filter 类型有 5 种，要全实现，约 150 行。
  → **选 (a)**，但把 ffmpeg 调用封装成 `decodePngToRgba(path)`，万一以后要换只改一处。

  > 需要注意 Windows 下管道读回二进制的坑。仓库既有的 `media.ts` 已有 ffmpeg 调用惯例，
  > 照它的写法来（`stdio: "pipe"` + 收集 Buffer），并在自检里加一条"读回的 w/h 与文件头一致"。

| `TILE_TOOLS` | 拼图工具名（刷子 / 装饰 / 建筑 / 橡皮） |

### 8.5 拼图编辑器交互基线

沿用骨骼模块装配台已经验证过的规格：

| 操作 | 行为 |
|---|---|
| 滚轮缩放 | **以光标为锚**（内容点在光标下不动） |
| 平移 | 空格 + 拖动，或中键拖动；复用舞台自身滚动，不引入第二套坐标 |
| `Ctrl/Cmd + 0` | 适应窗口（100% 且画布居中） |
| 撤销 / 重做 | 事务性 patch；≥ 20 步 |
| 刷子拖动 | 逐格更新，同格不重复 push 撤销栈 |

> **不要重犯装配台那两个坑**：撤销栈被 `updatedAt` 每次提交清空（撤销按钮永远是灰的）、
> `redo` 存的是改动前快照（重做是空操作）。tile 的编辑模型要一开始就把
> "撤销栈只由用户操作驱动"写进注释。

### 8.6 落盘时的写法

- 几何内核在宿主半区，浏览器半区的拼图预览需要一个**同构的轻量渲染器**。
  两个选择：
  - (a) 预览也走宿主：`runTileMap` 生成 PNG → `<img src="…/map/map.png?rev=…">`。
    **推荐**，零重复实现，`rev` 指纹（仓库既有做法）保证刷新。
  - (b) 浏览器半区用 canvas 自己画。
  → **选 (a)**。只有编辑时的"逐格即时反馈"需要 (b) 的一份简化版（`drawCellAt`），
    最终成果仍以宿主渲染的 PNG 为准。

### 10.2 `verify-tile.mjs` 必须覆盖的断言

**几何（G 系列）**

| # | 断言 |
|---|---|
| G1 | 模板渲染出的菱形比例 = `2.000 ± 0.005`，四顶点在规格位置 ±1px |
| G2 | 对 `research/probe/b8/*.png` 全部样本测量，`ratio ∈ [1.98, 2.02]` |
| G3 | 规整产物：`\|ratio − 2\| ≤ 0.05` |
| G4 | 规整产物：菱形内 `alpha < 250` 的像素数 = 0 |
| G5 | 规整产物：菱形外 `alpha > 8` 的像素数 = 0 |
| G6 | 边缘残差 ≤ 3px（源图尺度） |
| G7 | 洋红残留像素数 = 0 |
| G8 | 传入一张**全白图**（没有菱形）→ 走 template 回退，不抛异常 |

**拼图（S 系列）**

| # | 断言 |
|---|---|
| S1 | 同类地块铺 5×5：整体 alpha 无洞 |
| S2 | 同种子两次渲染 → `Buffer.equals` |
| S3 | 不同种子 → 变体分布不同（`cells` 相同、抽出的变体下标序列不同） |
| S4 | 跨格建筑锚点：贴图大菱形下顶点与 2×2 区域下顶点重合 ±1px |
| S5 | `cols=rows=1` 边界不崩 |
| S6 | 画布超限（64×64 单元格）→ 抛出明确错误而不是 OOM |

**装饰（D 系列）**

| # | 断言 |
|---|---|
| D1 | 装饰底部锚点 = 由 `settings` 推导出的值（64×96 下为 54）±1 |
| D2 | 装饰宽度 = 40 ± 4（或等比缩到高度上限） |
| D3 | 装饰 bbox 全在 `0 ≤ y < cellHeight` 内 |
| D4 | 前排地块绘制后覆盖后排装饰的下半部（比较两个像素位置） |
| **D5** | **无白边**：`alpha > 200` 且 `min(RGB) ≥ 220` 的像素数 **= 0**（研究期实测旧做法是 184） |
| **D6** | **保住抗锯齿**：成品的 alpha 取值个数 **≥ 64**（旧做法只有 2，即成品的 alpha 必须是软的） |
| **D7** | **剪影不被吃掉**：新做法的非透明像素数 ≥ 旧做法的 95%（实测 1185 vs 1186） |
| **D8** | **软 alpha 必须有死区**：喂一张纯白底图（只有压缩噪声，`dist ≤ 10`）→ 判定为「无前景」而抛错，而不是把整张底当成前景 |

> D5~D8 对应 §1.2 的 K9/K10（见下），是**必须写的反向验证测试**：
> 把 `matte_foreground` 换回「硬阈值 + 只改 alpha」，D5 与 D6 必须立刻失败。

**规整参数化（P 系列）**

| # | 断言 |
|---|---|
| P1 | `cellWidth=96, cellHeight=144` 时，菱形比例仍为 2.000，锚点按公式变化 |
| P2 | `cellWidth` 不能被 4 整除时，创建项目被拒并给出明确错误 |

### 10.3 反向验证回归测试（硬要求）

至少一条**去掉修复就失败**的测试，钉住 K1：

```
构造用例：取一张模板图，故意缩放到 1536（模拟上游被压缩）
断言：
  · template_diamond() 量出的宽 ≠ 硬编码的 1884
  · 用该模板几何走规整 → 产物菱形比例仍然是 2.000 ± 0.05
  · 若把 template_diamond() 换成硬编码常量 → 产物出现透明缺口（G4 失败）
```

第二条建议钉住 K4（装饰被画两遍）：

```
构造用例：一张"地面 + 树"的合成图
断言：
  · 不调用 toDecoratedCell（已废弃的实现）—— 断言该函数不存在或不被引用
  · 装饰走独立生成路径时，单元格内只有一个树冠 bbox
```

第三条必须钉住 K9/K10（白边，见 §10.2 的 D5~D8）：

```
构造用例：取一张真实的 2048² 白底装饰图
断言：
  · 成品里 alpha>200 且 min(RGB)≥220 的像素数 == 0        （旧做法实测 184）
  · 成品的 alpha 取值个数 >= 64                            （旧做法只有 2）
  · 新做法的非透明像素数 >= 旧做法的 95%                   （剪影不被吃掉）
反向验证：把 matte_foreground 换回「硬阈值 + 只改 alpha」，上面第一条与第二条必须失败。
```
