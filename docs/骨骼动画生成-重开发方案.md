### 两条值得记住的排查经验（都写进了代码注释）

1. **症状像「模型不行」，其实是自己的坐标错了。** 连续几次重绘都拿到「纯色」，
   我一度据此写下「seedream-5-0-pro 不擅长原地重绘」的结论并改了默认模型。

   教训：**在把失败归因给外部依赖之前，先证明自己送进去/取回来的每一步都对**。
   现在有一条反向验证过的回归测试钉住它（去掉修复就会失败）。
2. **探针一定要和产品共用代码。** 排查时我写了个探针脚本，但它自己拼了一份提示词，

## 0. 摘要

### 0.1 一句话结论

v1 的问题不是「自动装配不够准」，而是**整条链路只承认一种产物（一张自动拼好的骨架）**，于是 AI 的每一次判断失误都只能靠人重复劳动来补，而人的修正又无法被系统记住、无法局部生效。v2 要做的是把「**AI 给初值与语义、人给约束与审美、机器负责一致性与重算**」变成**数据模型层面的事实**，而不是流程层面的一句口号。

### 0.2 五个结构性瓶颈（v1）

| # | 瓶颈 | 证据 |
|---|---|---|
| 1 | **拆件是单点赌注**：一次生图决定成败，失败只能整张重来 | `riggen.ts:1013-1070`（唯一付费阶段）；实测角色被换掉（README:696-710） |
| 2 | **自动装配是「像素相似」而非「语义正确」**：重画过的部件在错误位置也能拿高分 | README:303-326（3/16 vs 13/16）；`rigpose.ts:1553-1730` |
| 3 | **骨架表达力只有「region + 固定 16 骨 + 硬编码 z 序」**：无 IK、无约束、无 mesh/FFD、无多皮肤 | `spine.ts:55-75, 91-108`；`spine.ts:630-788` |
| 4 | **动画是查表常量**：6 个预设写死在代码里，只对标准人形名生效，用户不能改一帧 | `spine.ts:220-554`；README:719-720 |
| 5 | **手工只能在「② 装配」这一个阶段出手**：骨骼、动画、层级关系都没有编辑面 | `client.ts:3740-4348`；README:383-415 |

### 0.3 v2 的七个动作

1. **把「文档」变成一等公民**：引入 `RigDocument`（§4.3），它同时是 AI 的输入输出契约、编辑器的操作对象、导出的唯一真源。
2. **引入「三通道姿势模型」**（§4.5，抄自 DragonBones `Bone.offsetMode`）：`origin`（绑定）/`offset`（手工）/`animationPose`（AI/动画）**相加**——从此 AI 重跑动画不会抹掉人摆的骨骼，人改骨骼也不会让动画失效。
3. **把流水线从 4 阶段拆成 9 阶段**，每一阶段都有独立的失效传播与局部重算（§4.2、§4.4）。
4. **定义 7 个 AI 出手点**，每个都配结构化 JSON 契约与「必须产出可视化证据」的硬要求（§5）。
5. **补齐 4 类手工编辑器**：骨骼编辑、层级/约束、时间轴 K 帧、贴图变体重绘（§6）。
6. **双格式导出**：Spine 4.2 与 DragonBones 5.5 共用同一份 `RigDocument`（§7）。
7. **预览渲染器按 DragonBones 求值链重写**，从「只有 rotate/translate 的播放器」升级为支持约束、mesh/FFD、slot 混合、多图层（§8）。

## 1. 现状诊断

### 1.1 v1 的四个阶段与数据流

```
① parts   runRigSheet(★花钱) → runRigSegment(免费)   → parts/*.png + sheet/parts-montage.png
② layout  runRigLayout(names?)                       → layout/composite.png + comparison.png + layout.json
③ rig     runRigBones                                 → rig/skeleton.json + rig/preview.html
④ atlas   runRigAtlas                                 → atlas/skeleton.png + skeleton.atlas
```

一处 `job.json` 承载全部状态（`riggen.ts:184-214` 的 `RigJob`），阶段间靠 `invalidateFrom` 置空下游（`riggen.ts:1528-1529`、`1667-1668`）。

### 1.2 v1 真正做对的事（v2 必须保留）

这些都是 v1 相对参考项目**已经更强**的地方，重开发时不能退回去：

1. **阶段化 + 局部重跑**。参考项目 `position_parts.py` 全文件没有任何 ROI/区域参数（`--reference/--parts/--output/--min-matches/--ratio/--debug` 六个，`:441-452`），自动定位一旦错，脚本层没有补救手段，只能人在编辑器里拖。v1 的 `runRigLayout({names})` 与 `setRigLayoutHints` 正好补上这个空缺（`riggen.ts:1395-1471, 1562-1592`）。
2. **网格 + 蒙太奇让「第几个格子 = 哪个部件」成为确定事实**（`spine.ts:30-75`、`riggen.ts:1240-1286`）。参考项目只会产出 `part_00.png … part_NN.png`（`split_character.py:157`），"改名"是整条链的硬前置且无任何校验。
3. **「agent 当视觉模型」的先验回环**（`riggen.ts:1562-1592` + `solveLayout` 的 `bounds`）。实测 3/16 → 13/16（README:321-326）。
4. **零外部依赖的自包含预览**（`rigpreview.ts:41-392`）。参考项目的 `generate_spine_player.py` 依赖 UNPKG CDN，却在 docstring 与 SKILL.md 里三处宣称 "self-contained"（`:160-161` vs `:4-6`、`:288`）。
5. **job 内局部写入而非整文件重生成**（`saveRigLayoutItems`，`riggen.ts:1618-1674`）。参考项目的纠正最终都要走到「给我一份完整的修正 JSON」（`adjustment-format.md:117-124`）。
6. **显式审核模式**（`setReviewMode`）与**结构化验收包**。参考项目靠 adjustments 文件链当审计。

### 1.3 五个瓶颈的机理

#### 瓶颈 1：拆件的单点赌注

`generateSheet` 只调一次 `generateImage`（`riggen.ts:1040-1049`），失败即整阶段作废。参考项目的 `split_character.py` 更糟：单次调用、无 seed、无重试、无部件数量断言，返回里找不到 `inline_data` 就 `sys.exit(1)`（`:72-93`）。

**v2 的修法**：拆件也要**分而治之**——不是「一张图拆 16 件」，而是「逐部件或按部位分组生成 + 每次生成后立刻做单件质量判定」，见 §4.2 阶段 1 与 §5.2。

#### 瓶颈 2：几何相似 ≠ 语义正确

`rigpose.ts:1553` 的 `solveLayout` 是 ZNCC 模板匹配（`rigpose.ts:773-843` 的 `znccAt`），排序分 `ZNCC × (0.3 + 0.7×覆盖率) + 证据项`。它在「平涂低细节」画风上必然失手（README:691-693），而且**重画过的服装裁片在错误位置也能拿到 0.48 的均分**（README:711-716），纯靠分数发现不了。

**v1 已有的两道兜底**（`riggen.ts:1486-1527`）：头在脚下面 → 判定不可信；均分 < 0.32 → 判定角色被换过。这是对的，但它是**事后告警**，不是**事前引导**。

**v2 的修法**：把「语义」从事后告警变成事前约束——**先让 AI 产出结构化的部件语义表（部位 + 父骨骼 + 锚点），再让几何去满足它**，而不是先盲搜再问「这合理吗」。见 §5.3、§5.4。

#### 瓶颈 3：骨架表达力不足

`buildSkeleton`（`spine.ts:630-788`）只能产出：
- 一根部件 = 一根骨骼（`boneNames = visible.map(p => p.name)`，`spine.ts:636`）；
- 固定 `RIG_SLOTS` 表推导父级（`spine.ts:55-75`），表外名字靠关键词猜（`spine.ts:130-143`）；
- 固定 z 序 `DEFAULT_DRAW_ORDER`（`spine.ts:91-108`）；
- region attachment（无 mesh、无权重、无 FFD）；
- 无 IK、无约束、无多皮肤。

对照 DragonBones 运行时具备而 v1 完全没有的能力（`_report_dragonbones.md` §3–§7）：

#### 瓶颈 4：动画是查表常量

`spine.ts:220-445` 六个 `gen*` 函数把每一帧的角度写死；`buildAnimations(boneNames, ids)`（`spine.ts:543-554`）只按名字过滤。README:719-720 自己承认：「只对标准人形骨骼名生效，部件名对不上就没有对应时间轴」。

而且**参考项目同样如此**：六个预设只产生 `rotate` 与 `translate` 两条轨道，**没有 scale 轨道**（`build_spine_json.py:166-473`），所以没有真正的 squash & stretch、没有弧线控制、没有循环接缝校验（`SKILL.md:1944` 只有一句人肉约定，脚本不校验）。

**v2 的修法**：动画从「函数」变成「**数据 + 参数**」——预设降级为可编辑的初始值，动画本身进 `RigDocument` 可被 AI 覆写、可被人 K 帧（§4.3、§6.6）。

#### 瓶颈 5：手工只覆盖一个阶段

`RigAssemblyEditor`（`client.ts:3740-4348`）是全项目最完整的手工能力，但它只作用于 `layout.items`（x/y/宽/高/旋转/z）。骨骼、动画、皮肤没有任何编辑面。

**v2 的修法**：把「一次编辑 = 一个事务性 patch 到 `RigDocument`」做成统一模型（§6.1），编辑器只是它的视图。

## 2. 三个参考源给了什么

### 2.1 spine-animation-ai（顶层纯脚本流水线）

**它的结构特征：确定性脚本包办几何，LLM 承担全部语义判断。**

`SKILL.md:41-1763` 是 5 个脚本的原文（经逐字节比对 5/5 IDENTICAL），prose 只在 `Step 1/1.5/2` 让模型看图判断。真正需要模型的地方有 8 处（`_report_spine_ai.md` §7.1），最要紧的三处：

1. **部件语义命名**（`SKILL.md:1815-1816`）——因为脚本只给 `part_NN.png`；
2. **骨骼的 parent/x/y/length**（`build_spine_json.py:490` 只用名字集合做存在性判断，**没有任何层级推导**）；
3. **装配失败诊断与偏移修正**（`SKILL.md:1850-1854`）。

**一个致命的结构性断裂（对 v2 最有价值的教训）**：`position_parts.py:477-484` 的输出 `{reference_image, canvas_width/height, parts, z_order}` **不是** `build_spine_json.py --config` 的合法输入（需要 `bones`/`slots`/`attachments`，`:490` 立刻 KeyError），而 `README.md:139-143` 却把这套命令写成了标准流程。「定位结果 → 骨骼配置」这一步**既没有脚本也没有文档**，每轮都要 LLM 现编胶水——这正是「任何改动都只能整体重跑」的结构性根因。

> **v2 的直接对治**：`RigDocument` 必须让「装配结果」与「骨骼配置」**是同一份数据的两个视图**，中间不存在需要 LLM 现编的胶水。

**它真正值得抄的知识资产只有两处**：

- `build_spine_json.py:92-153` 对 Spine 4.2 wire format 四条地雷的精确处理（见附录 A）；
- `position_parts.py:253-326` 的**遮挡投票定序**：两两求 AABB 交集 → 按重叠面积采 ~500 点 → 在双方 alpha≥128 且参考图 alpha≥128 的像素上比「谁的 RGB 更接近参考图」（5 单位死区）→ 一方超 1.2 倍才记票 → 加权深度和升序即从后到前。
  - **注意它的坑**：从不与任何件重叠的孤立件 `depth=0` 会飘到排序中间；实现时必须给孤立件确定性兜底（建议按 y 中心 + 面积）。
  - 实证它确有必要：`examples/sombrero/adjustments-example.json:59-70` 与 `layout_corrections.json:154-165` 对同一角色给出**不同的腿部前后顺序**——人工纠正的主要内容包含 z 序重排。

**它的人工纠正契约**（`docs/adjustment-format.md:28-46`）值得原样搬：

```json
{ "adjustments": {
    "part-name": {
      "original_offset": { "x": 0, "y": 0 },
      "user_offset":     { "dx": 0, "dy": 0, "drot": 0 },
      "final_offset":    { "x": 0, "y": 0 } } },
  "draw_order": [ "…从后到前…" ] }
```

四条性质（`:5-9`）：Readable / Reversible / Composable / Auditable。并且 `:48-60` 明确要求**零位移也要记录**——「This is intentional — it confirms the part was reviewed, not skipped」——这可以直接用作「这一步人来过」的凭证。

**它的失败模式**（`_report_spine_ai.md` §8）：拆件无校验、抠图是硬阈值且**完全不看 alpha 通道**（`split_character.py:118`）、无 proximity grouping、旋转被双向封死（`abs(rotation)>20` 拒 / 模板兜底恒 0°）→ **实质是「无旋转 rig」**、静默丢件（`:208-210`、`:244`）、图集对超宽件无扩宽分支导致 `paste` 静默裁切但 `.atlas` 仍写完整 size、预览依赖 CDN。

### 2.2 reskin-app（可视化编辑器 + AI 服务抽象）

**先纠正三个容易误判的前提**（`_report_reskin_app.md` 已核实）：

1. `SpineCanvas.tsx` **没有自研 Spine 渲染器**——直接用官方 `@esotericsoftware/spine-pixi-v8`（`package.json:12`、`SpineCanvas.tsx:285`）。应用自己只实现了：资源加载与缓存击穿、皮肤切换、一次性自动 fit、逐 attachment 命中测试、attachment 级变换读写、隐藏 slot。
2. **没有 zoom/pan**（grep 全前端 `zoom|wheel|pan|ResizeObserver` 零命中），只有加载时一次 `spine.scale.set()`，`padding=40` 硬编码。
3. `ai/base.py` 的 Protocol **名存实亡**：`GeminiProvider.edit_image` 签名更宽、`SAMProvider` 根本没有 `segment()`、`Component` 从未被实例化、`ai/sam_stub.py` 是死代码。

**它做的事**：把「已渲染的角色图 + 已打包的 atlas」丢给 Gemini 做整体换皮 → SAM/Bria+连通域把结果切回每个 slot → 重打包 atlas → 写一份新的 `Spine-{skin}.json`。

> ⚠️ **这个「换皮闭环」不进入 v2**（§3.1 的范围裁剪：不导入外部骨架、不做换皮）。本节只保留它对 **AI 重绘单张贴图** 这件事的工程经验（宽高比对齐、遮罩回贴、逐件回退、快照日志），以及它的架构反面教材（无作业模型、两套变换语义冲突）。

**四个 AI 任务的精确分工**：

| 任务 | 实现 | 关键点 |
|---|---|---|
| 文+图 → 图（换皮/重绘） | `ai/gemini.py:62-180` | **宽高比对齐 + 白底 padding + 1:1 裁回**（`:207-232`、`:168-177`）——把「生成模型会改画幅」消灭在进入流水线之前。**最值得抄的一招** |
| bbox 提示式分割 | `ai/sam_provider.py:43-92` | **一次 `set_image()` embedding + N 个 box prompt**，N 个 slot 只 1 次 HTTP。协议形状：`{image_base64, boxes:[{slot_id,x_min,y_min,x_max,y_max}]}` → `{masks:[{slot_id,score,mask_b64}]}` |
| 无模型 CV 兜底分割 | `ai/cc_segment.py:72-111` | 抠背景 → 8 连通域 → **用「你原本就知道的」部件剪影做 IoU 模板**匹配 |
| 抠背景 | `ai/bria.py:48-107` | 只有它，不是分割也不是生成；失败优雅降级 |

**⚠️ 没有真正的 mask-conditioned inpaint。** 「Retouch」是把 slot 整张 bbox 裁剪图丢回 Gemini + prompt 求它保持轮廓（`server.py:614-624`），遮罩是**事后 alpha 相乘**（`atlas_rebake.py:343-345`）。这是「文本引导 + 事后 alpha 裁剪」。

**它值得抄的工程经验**：

- **遮罩 = alpha 相乘 + 按部件尺寸分档腐蚀**（`atlas_rebake.py:320-345` + `settings.py:29-38`，默认 px `0/1/2/3`，阈值 `60/200/500`）。「AI 生成的部件边缘一定有白晕」是这类流程的普遍问题；形态学 close 补洞 + 分档 erode、且**细部件腐蚀半径更小**是很实在的经验。
- **非破坏性的逐 slot 变换增量**（`SpineCanvas.tsx:627-651`）：存 `x - orig.x`、`scaleX / orig.scaleX`、`rotation - orig.rotation`，**丢弃等于默认的字段**，重置 = 删文件。
- **快照式管线日志**（`logs.py:1-14`）：因为所有操作都原地覆写文件，只记路径永远只能看到"最后一次"的像素——**必须在每次操作时把输入/输出拷出来**。
- **服务端改写 atlas 文本的 PNG 行注入 `?v=` cache-buster**（`server.py:195-208`）：atlas 里是裸文件名，URL 相对解析会丢 query，导致「atlas 重载了但 PNG 还是旧的」。
- **逐 slot 回退原图**（`reverted_slots.json`）：一个小 JSON 记录 + 重打包时查表。

**它最大的架构债（v2 必须避开）**：**没有作业模型**。`reskin_generate` 同步 await 整条 Gemini 流水线（`server.py:743-795`），`_State` 是类级可变单例且无锁（`:62-81`），`_rebuild_skin_atlas` 开头 `unlink()` 全部 baked（`:484-485`）。以及**两套变换机制语义冲突**：CanvasTools 拖拽 → 服务端持久化（渲染期生效）；PartEditor 滑杆 → 客户端内存（只在 export 时烘焙）——结果「画布上拖好的位置导出后全丢」「调滑杆时画布上的角色完全不变」。

> 这两条正是 §4.5「三通道姿势模型」与 §4.1「作业/事务模型」要解决的东西。

### 2.3 DragonBonesJS（表达力上限与数据模型）

这是三者中**唯一给出完整运行时语义**的源。对 v2 而言，它的价值不在格式，而在**三个数据模型决策**：

#### ★ 决策一：`origin + offset + animationPose` 三通道（v2 的地基）

`armature/Bone.ts:109-171`，`_updateGlobalTransformMatrix` 里（已核实原文）：

```ts
// Bone.ts:95   offsetMode 默认 Additive
// Bone.ts:127-134
global.x        = origin.x        + offset.x        + animationPose.x;
global.scaleX   = origin.scaleX   * offset.scaleX   * animationPose.scaleX;
global.scaleY   = origin.scaleY   * offset.scaleY   * animationPose.scaleY;
global.rotation = origin.rotation + offset.rotation + animationPose.rotation;
global.skew     = origin.skew     + offset.skew     + animationPose.skew;
```

`origin` = 绑定姿势（`Bone.ts:360` `this.origin = this._boneData.transform`）、`offset` = 手工偏移、`animationPose` = 动画输出。三者**相加**，`OffsetMode{Additive(默认), None, Override}` 决定语义。

**这就是「AI + 手工」共存的正确地基**：AI 写 `animationPose`（时间轴），美术拖骨骼写 `offset`，两者互不覆盖。配合 `Bone.invalidUpdate()` / `Armature.invalidUpdate(name, true)` 做局部失效。示例见 `Pixi/Demos/8.x/src/BoneOffset.ts:39-52`。

#### ★ 决策二：curve 是贝塞尔控制点 + 运行时重采样

`ObjectDataParser.ts:147-221` 的 `_samplingEasingCurve`：长度 `%3==1`（= 6n-2，如 4）为紧凑式（首锚 (0,0)、末锚 (1,1) 省略），二分法解 x(t) ≈ t 重采样成 `frameCount+1` 个采样值（×10000 存 int16）。

工具侧应当**写控制点（4 或 6n-2 个数），不要预采样**。配套的 `tweenEasing` 单标量符号编码极省 token（`ObjectDataParser.ts:1462-1489`）：缺省 `-2`=阶跃、`0`=线性、`(-1,0)`=QuadIn、`(0,1]`=QuadOut、`>1`=QuadInOut。

⚠️ **「没有 tweenEasing 字段」= 阶跃，不是线性**——手写 JSON 最常踩的坑。

#### ★ 决策三：`slotPose + bonePose + weights` 自包含蒙皮契约

`ObjectDataParser.ts:2120-2164`：顶点先过 `slotPose`，再乘 `invert(bonePose)` 得骨骼局部绑定坐标，写进 `(weight, x, y)` 三元组。**蒙皮信息自包含，运行时无需外部绑定姿势。**

> 对 v2 的意义：**「AI 自动绑权重」只要产出这三个数组即可闭环**（§5.5）。

#### 其他值得抄的（按性价比）

| 借鉴点 | 出处 | 对 v2 的用途 |
|---|---|---|
| `cacheFrameRate` 帧级矩阵缓存（10 float/骨骼/帧） | `ArmatureData.ts:282-317`、`Bone.ts:427-433` | AI 批量生成后逐帧预览/比对/烘焙的交互延迟关键 |
| `frameIndices`：每帧 → 关键帧下标表 | `ObjectDataParser.ts:1271-1305` | 时间轴 scrub 刚需，O(1) 查询 |
| `BlendState` 层级权重分配（20 行） | `AnimationState.ts:1528-1601` | 分层混合；配合 `addBoneMask/removeBoneMask` |
| `resetToPose` + `displayControl` | `AnimationState.ts:66, 81, 923-939` | **切动画姿势残留的官方答案** |
| PathConstraint 沿贝塞尔摆骨链 | `Constraint.ts:230-834` | AI 生成飘带/鞭子/绳索/头发的**最优载体**：AI 只输出一条路径 + 参数 |
| Surface 分片仿射 | `Surface.ts:66-88, 165+` | 裙摆/旗帜/软体，比逐顶点 FFD 更不易穿模 |
| `inheritScale/Rotation/Translation/Reflection` 四开关 | `Bone.ts:239-299` | 防「父级非均匀缩放把子级拉成斜切」 |

| `SlotColor` 的 `pow(fadeProgress,4)` 指数逼近 | `TimelineState.ts:773-783` | 过渡中可再次改目标 |
| `share`（Linked Mesh） | `ObjectDataParser.ts:401-420` | 同款多配色零膨胀 |

#### 需要规避的坑

- **IK 只有 2 骨**（`chain≥2` 与 1 等价）、**无 `TransformConstraint`**、`ConstraintData.order` 声明了但解析器从不赋值（`Parser` 全仓 grep `.order` 只有 `_onClear` 一处）。
- `Transform.fromMatrix` 的负缩放/±π 分支（`Transform.ts:201-226`），照抄一半会在 `|rotation|≈90°` 抖 ±π。
- **`displayFrameCount` 与帧动画索引强耦合**：多套贴图并存时 display 顺序必须与原皮一致，否则 `SlotDisplay` 时间轴错位。（v2 暂不启用多套贴图，故此条只在将来重开时生效。）
- `edges`/`userEdges`/`format` 是编辑器字段，运行时完全不读。

## 3. v2 的目标、成功判据与非目标

### 3.1 两条输入路径 + 一条迁移路径

| 路径 | 起点 | 谁主导 |
|---|---|---|
| **A. 生图拆件** | 一张角色整图 | AI 全自动 + 人工验收 |
| **B. 上传部件** | 用户自己的部件 PNG（文件名即部件名） | 人工给料 + AI 装配 |
| **M. 历史任务迁移** | 本插件 v1 创建的 rig 任务（`job.json`） | 自动迁移，人工确认 |

**已明确的范围裁剪（2026-09 决策）**：

- ❌ **不做外部工具产出的骨架（Spine / DragonBones / 其它编辑器）的导入与编辑**。reskin-app 那条「导入现成骨架 → 换皮 → 重打包」的闭环**不进入 v2**。
- ❌ 相应地，**不做面向外部骨架的语义对齐、图集反向切分（explode）、skin 写回**。
- ✅ **但本插件自己创建的历史任务必须能继续打开**——走路径 M，由 §10.4 的迁移器把 v1 的 `job.json` 转成 v2 的 `document.json`。

**这个裁剪带来的连锁简化**（下面各节已同步）：

1. **不再需要把「整张重绘结果切回各个 slot」**。reskin-app 之所以要 SAM / 连通域 / IoU 模板（`cc_segment.py:72-111`）是因为它把**整张 atlas 或整张合成图**丢给 Gemini 重绘，回来必须再切一遍。v2 是**逐部件重绘**，一个部件进、一个部件出，天然不需要反向切分（§5.8）。
2. **不再需要解析外部骨架的完整 schema**（骨骼层级、mesh、weights、约束、多皮肤）。v2 只解析**自己写出的**两种格式，且只为自己验证（§11.2 A2）。
3. **DragonBones 导出保留**（导出 ≠ 导入），但**DragonBones 导入解析器不做**。
4. **「多皮肤」从核心降级为可选**（§6.7）：数据结构与导出保留（格式天然支持、成本近零），但**不做面向换皮的多套具名皮肤与运行时切换**；编辑器只做「同骨架内的贴图变体：重绘 / 换色 / 逐部件回退」。

> **如果将来要改主意**：M0–M5 的求值器与 `RigDocument` 已经覆盖了外部骨架的绝大部分结构，届时的边际成本主要在「语义对齐」与「图集 explode/重打包」两处，而不是重写求值器。所以这个裁剪是**可逆**的。

### 3.2 成功判据（可度量）

| # | 判据 | 现在 | v2 目标 |
|---|---|---|---|
| M1 | **装配命中率**（真实立绘 + 生图拆件） | 3/16（无先验） | ≥ 12/16（AI 先验 + 语义约束） |
| M2 | **改一处的重算代价** | 全阶段重跑 | 改 `layout` 单项 → 只重跑 rig+atlas；改动画曲线 → 只重跑 rig |
| M3 | **AI 重跑动画后人工骨骼修正是否丢失** | 会丢（无此能力） | **不丢**（三通道模型） |
| M4 | **导出可被官方工具打开** | Spine 4.2（已验证） | Spine 4.2 + DragonBones 5.5 双通过 |
| M5 | **离线打开预览** | ✓ | ✓（保持） |
| M6 | **人工编辑的操作数**（把一张立绘调到位） | 无法完成（无从下手） | ≤ 20 次操作 + 全部可撤销 |
| M7 | **每一步都能被 AI「看懂」** | 部分（仅对比图） | 每阶段强制产出可视化证据（§5.7） |

### 3.3 非目标（明确不做，避免范围蔓延）

- **不做外部工具产出骨架的导入与编辑**（决策见 §3.1）。包括：Spine / DragonBones 工程文件的编辑、换皮、图集反向切分、skin 写回。
- **不做 3D / 骨骼网格变形到 3D**。
- **不做骨骼动画的物理仿真**（布料/弹簧求值）。Surface 只做分片仿射，不做质量-弹簧。
- **不做时间轴上的逐帧手绘（帧动画）**。骨骼动画的定位是「拆件 + 变换」。
- **不做账号/多人协作**。仍是单机单用户。
- **不引入 Python / OpenCV / numpy 依赖**。全部跑在插件进程（Node）与浏览器（经典脚本）里——这是 v1 已经确立且要坚持的约束（README:276-277）。

## 4. v2 总体架构

### 4.1 六层

```
┌─ L6 运行时层 (rigruntime)  ── 求值链：bone world → constraint solve → slot display → mesh deform → draw
│                               宿主离线渲染（合成图/验收图）+ 客户端实时预览，同一份求值器
├─ L5 导出层   (rigexport)   ── RigDocument → Spine 4.2 JSON+atlas / DragonBones 5.5 JSON+tex.json
│                               + 自包含 preview.html（内联求值器）
├─ L4 编辑层   (client 的 rig 段) ── 4 类编辑器：装配台 / 骨骼 / 时间轴 / 皮肤
│                              全部 = 对 RigDocument 的事务性 patch（§6.1）
├─ L3 AI 层    (rigai)       ── 7 个出手点，每个都有结构化 JSON 契约 + 可视化证据（§5）
├─ L2 算法层   (rigpose / rigsolve / rigbind) ── 纯计算、无 I/O、可单测：
│                              分割 · 模板匹配 · 遮挡投票 · 骨骼推导 · 自动权重 · 图集装箱
├─ L1 文档层   (rigdoc)      ── RigDocument = 单一真源（§4.3）+ 依赖图与失效传播（§4.4）
└─ L0 作业层   (riggen)      ── job/事务/锁/进度/日志（重写：reskin-app 最大的债就是没有它）
```

**分层硬约束**（与 v1 的既有工程纪律一致）：

- L2 不碰文件系统（v1 的 `rigpose.ts` / `spine.ts` 已经做到，README:668-670）；
- L1 是唯一的真源，**任何产物的内容都能从 `RigDocument` 重新算出来**，磁盘上的 PNG/JSON 都是派生物；
- L3 只能通过**受限 JSON patch** 改 L1，不能写代码、不能写死像素（§5.5）；
- L4 与 L3 走**同一条 patch 通道**——这是「AI 与手工平等」的机制保证，而不是口号。

### 4.2 九阶段流水线（v1 的 4 阶段 → v2 的 9 阶段）

```
① intake   选路径（A 生图拆件 / B 上传部件 / M 历史任务迁移）+ 问清参数       ★0 花费
② parts    拆件：生图或导入 → 分割 → 部件图 + 蒙太奇                             ★花钱(路径A)
③ semantic 语义表：AI 给出「部件 → 部位/父骨骼/锚点/别名」+ 结构校验              ★AI 调用
④ layout   装配定位：AI 先验 → 模板匹配 → 冲突/遮挡/镜像消解 → 对比图            免费本地
⑤ skeleton 骨骼与绑定：层级、锚点、约束、可选 mesh 与权重                        免费本地
⑥ animate  动画：预设实例化 + AI 编排 + 人工 K 帧                                 ★AI 调用(可选)
⑦ texture  贴图变体：逐部件重绘 / 换色 / 版本回退（同一骨架，不涉及外部骨架）      免费本地
⑧ atlas    图集：装箱 + .atlas / tex.json + 硬校验                               免费本地
⑨ export   导出：Spine / DragonBones / 预览 HTML / 引擎资源包                    免费本地
```

相对 v1 的四个新增阶段，每一个都有明确的「为什么必须独立」：

| 新阶段 | 为什么不能塞进别的阶段 |
|---|---|
| ③ semantic | 语义是**装配与骨骼的共同输入**。v1 把它藏在「网格位置 = 身份」的假设里（`spine.ts:30-36`），一旦模型不按网格摆就整条链失效（`riggen.ts:1299-1307`）。独立成阶段后，语义可以**先于几何**被确认与修改。 |
| ⑤ skeleton | v1 把「推骨骼」与「生成动画」混在 `buildRigOutput`（`riggen.ts:1833-1912`）里。分开后，改骨骼不必重跑动画数据（动画按**骨骼名**索引，改名才需要重映射）。 |
| ⑥ animate | 动画是**最需要 AI 与人工交替修改**的一层。v1 它是代码常量（`spine.ts:220-445`），改一次要动源码。 |
| ⑦ texture | 逐部件重绘/换色后要能**局部回退**（「这张 AI 头发不行，换回原版；其它保留」）。它是 layout 与 atlas 之间的一个独立可重跑环节，与骨骼无关。 |

### 4.4 依赖图与失效传播

v1 用的是「粗暴置空下游」：`fresh.rig = { status: "empty" }; fresh.atlas = { status: "empty" }`（`riggen.ts:1528-1529`、`1667-1668`、`1897`）。这在 v1 只有 4 阶段时还能接受，v2 有 9 阶段就太贵了。

**v2 用一张显式依赖图**：

```
parts ──▶ semantic ──▶ layout ──▶ skeleton ──▶ animate ──▶ export
             │            │           │  ▲                     ▲
             │            │           ▼  │                     │
             └────────────┴──────▶ skin ─┴──▶ atlas ───────────┘
```

规则：
- **节点内的细粒度失效**：改 `layout.items["head"].x` → 只让 `skeleton.head` 及其子骨骼的 `origin`、`skins.*.attachments.head` 失效；**装配层之外的一切不动**。
- **改名/改父级是重失效操作**：动画按骨骼名索引，改名要重映射 `animations.*.bones` 的键（DragonBones 的 `AnimationData.boneTimelines: Map<名字>` 与 Spine 的 timeline 键都是名字，不一致会**静默不生效**——见 `_report_dragonbones.md` §6.3）。
- **`offset` 变更不失效任何下游**：这是三通道模型的红利（§4.5）。
- 每次失效都写日志，并把「为什么重算」写进验收包。

**实现建议**：不引入通用图框架。`RigDocument` 的每个顶层段实现一个 `dependents(changedPath): string[]` 纯函数即可；v2 的阶段数（9）与依赖规模（十几条边）远在需要框架的阈值之下。

### 4.5 ★ AI 与手工的共存模型：三通道

这是整个方案最重要的一条，直接照搬 `DragonBones/armature/Bone.ts:109-171`（已核实原文）：

```
local = origin ⊕ offset ⊕ animationPose        // ⊕ 对 x/y/rotation 是加法，对 scale 是乘法
```

| 通道 | 谁写 | 什么时候写 | 被谁影响 |
|---|---|---|---|
| `origin` | 装配/骨骼阶段（几何算出来 + AI 提案 + 人确认） | 改 layout、改锚点、改父级 | 重跑 layout/skeleton 会重算 |
| `offset` | **人**（骨骼编辑器拖拽、旋转、数值输入） | 随时 | **任何自动重跑都不动它** |
| `animationPose` | AI 编排 + 人工 K 帧（时间轴） | 改动画 | 切动画时归零重算 |

**这一条解决了 v1 与两个参考项目共同的核心痛点**：

- v1：`buildSkeleton`（`spine.ts:630-788`）每次都从 `layout.items` 全量重算骨骼，人没有任何「只改一根骨头」的入口。
- reskin-app：两套变换机制语义冲突（§2.2），「画布上拖好的位置导出后全丢」。
- spine-animation-ai：纠正的唯一载体是整体重算的 `skeleton.json`（`adjustment-format.md:117-124`）。

**同时它给 AI 一个安全网**：AI 重跑 `animate` 阶段时，`offset` 里的手工修正天然保留；AI 重跑 `skeleton` 时，只覆盖 `origin`，人在 `offset` 里的偏置依然生效。**AI 可以放心地「重新想一遍」，而不必担心抹掉人的工作。**

**与 v1 现有 `rotation` 字段的衔接**：`layout.items[name].rotation` 是「部件相对参考姿态拧的角度」（`spine.ts:739`），它属于 **`origin` 的一部分**（因为它决定静止姿态的外观），不是 `offset`。人手拧的角度进 `offset.rotation`。这一点必须在实现时写清楚，否则会出现「同一个角度被算两遍」。

### 4.6 作业与事务模型（补 reskin-app 最大的债）

`reskin-app` 的所有问题是同一个根因的下游表现：**没有作业模型**（`_report_reskin_app.md` §7.6）。

v2 的做法（大部分 v1 已有，需要补齐的是事务性）：

| 需求 | v1 现状 | v2 |
|---|---|---|
| 任务状态机 | ✓ `RigJob` + `NodeStatus` + `running` 集合（`riggen.ts:1000-1008`） | 保持，改为按 `RigDocument` 的节点状态 |
| 并发保护 | ✓ `assertIdle` + `kick`（`riggen.ts:1000`） | 保持，并把「单任务单阶段」扩展为「单任务内阶段可并行（layout 与 animate 依赖不同）」 |
| 进度 | ✗ 只有 `running` 布尔 | 每阶段上报 `progress{phase, done, total, message}`，供 UI 与 `game_material_wait` 使用 |
| 取消 | ✗ | 每阶段检查 `AbortSignal` |
| 原子性 | ✓ `writeJsonAtomic`（`jsonio.ts`） | 扩展到「派生产物写临时目录 → 成功后原子替换」，避免 reskin-app 那种 `unlink()` 全部 baked 的中间态 |
| 编辑事务 | 半（`saveRigLayoutItems` 批量） | 显式 `applyPatch(docId, patches, {by:"human"\|"ai", label})`，返回 `{revision, invalidated, undoToken}` |

## 5. AI 出手点

### 5.1 分界原则

> **AI 负责「这是什么」和「这样好不好」；脚本负责「在哪里」和「对不对」。**

| 归 AI | 归脚本 |
|---|---|
| 部件叫什么、属于哪个部位 | 部件在像素上的包围盒 |
| 这块部件大概在参考图哪个区域 | 在该区域内精确到亚像素的位置/尺度/旋转 |
| 头应该挂在脖子下还是躯干下 | 骨骼的 `origin` 如何从锚点换算到父级局部系 |
| 这个动作的节奏对不对、幅度够不够 | 关键帧的 bezier 控制点如何绝对化 |
| 这个装配结果是否可信 | ZNCC 分数、覆盖率、结构自洽校验 |
| 这张贴图应该怎么重绘 | 遮罩怎么相乘、边缘怎么腐蚀 |

**三条硬约束**（防止 AI 越界造成不可复现）：

1. AI **只输出 JSON**，不输出代码、不输出像素。所有落盘产物都由脚本从 JSON + 输入图算出。
2. AI 的输出必须**带作用域**：`{target, field, value, reason}`，而不是「给我一份新的 document.json」。理由：局部 patch 才能触发 §4.4 的细粒度失效；整文件替换等于全量重算。
3. AI 的每个判断必须**配套一张它看过的图**，写进 `provenance.evidence`。理由：v1 的实测已经证明「分数高不代表摆得对」（`riggen.ts:1482-1485`），只有人能/能复核 AI 的复核。

### 5.2 出手点 1：拆件提示词（阶段 ②）

**v1 的做法**（`riggen.ts:266-294`）：要求模型按 `4×4` 网格摆放 16 个标准人形部件，**格子位置 = 部件身份**。

**v2 的改进**（不是推翻，是分层）：

- **保留网格**（它解决了参考项目「`part_NN` 无语义」的硬伤），但把「网格 = 身份」降级为「网格 = 提案」，真正的身份由阶段 ③ 确认。
- **新增：按部位分组生成**。对体型复杂的角色，「一张图 16 件」是超载的。支持 `groups: ["head", "torso", "arms", "legs"]` 分别生成，每次只出 4 件，单件失败只重生成那一组。**这把瓶颈 1 的单点赌注变成了可增量修复的 4 次小赌注。**
- **新增：单件质量判定**（本地，免费）。每次分割完立刻算：不透明像素占比、包围盒是否贴格线、是否与邻格连通域粘连。不合格直接标记 `needsRegen`，**不必等到装配阶段才发现**。
- **沿用 v1 的负面提示词**（`riggen.ts:292`）与 v1 已确立的软 alpha 边缘处理（README:340-365：形状由硬掩码决定 + 完全封闭孔洞填充 + 过渡只在最外圈 2-3px，**与颜色无关**）——**这一条 v1 做得比两个参考项目都好**（`split_character.py:118-120` 对灰度做硬阈值且完全不看 alpha 通道），必须保留。

### 5.3 出手点 2：部件语义表（阶段 ③，新增）

**输入**：`parts-montage.png`（部件蒙太奇，带格线，按 `partsOrder` 从左到右、从上到下排列——v1 已实现，`riggen.ts:1240-1286`）+ 参考整图。
**输出**：受限 JSON。

```jsonc
{
  "parts": [
    { "name": "head",       "role": "head",     "parent": "neck",
      "confidence": 0.95, "note": "含发箍与鲸鱼发饰" },
    { "name": "skirt",      "role": "accessory","parent": "hip",
      "confidence": 0.6,  "note": "裙摆是独立裁片，覆盖参考图 520-680px 区域" },
    { "name": "ribbon",     "role": "accessory","parent": "torso",
      "confidence": 0.4,  "note": "看不出是什么，可能是围裙带" }
  ],
  "warnings": ["第 9 格与第 13 格看起来是同一件东西的两半"]
}
```

**必须做的校验**（脚本侧，免费）：

| 校验 | 规则 | 违反时 |
|---|---|---|
| `role` 合法性 | 必须在枚举内（`head/neck/torso/hip/upperArm/lowerArm/hand/upperLeg/lowerLeg/foot/accessory`） | 拒绝该条，回落 `accessory` |
| 父级存在性 | `parent` 必须在 `parts[].name` 里，或为 `null` | 拒绝，回落 `torso` |
| **无环** | 沿 `parent` 链不得回到自身 | 拒绝，挂 `root`（v1 已有这个保护，`spine.ts:640-656`，但它是**运行时兜底**；v2 要**在写入前拒绝**） |
| 人形结构自洽 | 若角色被判定为人形（存在 `head` 与至少一条腿），则 `head` 必须是最上层祖先链末端、`foot` 必须在 `leg` 之下 | 报错并请 AI 重出该条 |
| 置信度分层 | `confidence < 0.5` 的条目标记 `needsHumanConfirm` | 在验收包里显式列出 |

**为什么值得独立成一个 AI 调用**：v1 里「这个部件是谁」由网格位置决定（`riggen.ts:1186-1206` 的 `cellOfGroup`），一旦模型不按网格摆就整条链失效，只能告警（`riggen.ts:1299-1307`）。独立后，**语义错了可以只改语义**，不必重新生图。

**并且它是装配阶段的输入**：`parent` 直接给出「谁该压在谁上面」的初始 z 序（`parent` 在链上更靠根的画在后面），比 v1 的固定 `DEFAULT_DRAW_ORDER`（`spine.ts:91-108`）更能容纳非标准角色。

### 5.4 出手点 3：视觉先验（阶段 ④，v1 已有，需要扩展）

**v1 已经做对**（`riggen.ts:1562-1592` + README:303-326）：agent `read_image` 看参考图与蒙太奇 → 给每个部件一个「大致在哪」的像素框 → `setRigLayoutHints` → `runRigLayout`。实测 3/16 → 13/16。先验框向外放宽 35%，只约束模板**中心**。

**v2 的三点扩展**：

1. **从「框」升级为「框 + 锚点」**。只给框，匹配仍可能把部件放到框内错误的位置（例如把两只手都放到同一个框里）。增加一个可选字段 `anchor: "top-center" | "center" | "bottom-center"`，让匹配知道「部件的哪一点应该落在框的哪一点」。
2. **局部重跑要先解除先验**。v1 已经踩过这个坑并做了正确判断（`riggen.ts:1425-1427`）：局部重跑时不带先验，否则「重新自动定位」会变成「又回到我上次说的那个位置」。v2 保留这一条，并在 UI 上明示「本次重跑未使用先验」。
3. **双向回环**：装配完成后，把 `composite.png` **再给 AI 看一眼**，让它回答「哪些部件看起来还不对、大概偏了多少、往哪个方向偏」，直接产出 `layout` patch。这是把参考项目的「Compare composite vs reference with Claude's vision and adjust layout JSON offsets」（`SKILL.md:1853-1854`）变成**结构化的一步**，而不是让用户自己在对话里描述。

### 5.5 出手点 4：骨骼层级与锚点（阶段 ⑤，新增）

**背景**：参考项目的 `build_spine_json.py` **没有任何层级推导**，骨骼的 `parent/x/y/length` 全靠 LLM 手写（`_report_spine_ai.md` §1.2）；v1 靠固定 `RIG_SLOTS` 表（`spine.ts:55-75`）。两者都不够。

**v2 的做法：AI 提案 + 几何求解 + 结构校验**。

- **几何先算出来**（免费、可复现）：沿用 v1 的算法——骨骼原点取部件近端锚点、朝向取近端→远端、`x/y` 逆旋转到父骨骼局部系（`spine.ts:619-745`，且 `scripts/verify-rig.mjs` 断言初始姿态偏差 < 0.02px）。**这部分不要让 AI 做**，它是纯几何。
- **AI 只提案三件事**：① 父级关系（尤其是非人形/多肢体角色）；② 「哪一端是近端」（这是语义，例如裙摆的近端在上沿、头发的近端在发根）；③ 额外关节的插入（例如「这条尾巴应该拆成 3 节，而不是 1 节」）。
- **结构校验**（脚本）：无环、父级先于子级（拓扑排序）、长度 > 0、锚点落在部件包围盒内。

**输出契约**：

```jsonc
{ "patches": [
    { "target": "parts.skirt", "field": "parent", "value": "hip", "reason": "裙摆挂在胯部，随胯摆动" },
    { "target": "parts.skirt", "field": "proximal", "value": [0.5, 0.0], "reason": "裙腰在上沿" },
    { "target": "parts.hair",  "field": "split", "value": ["hair-1","hair-2","hair-3"],
      "reason": "长发应分 3 节才能做出跟随感" } ],
  "evidence": "sheet/parts-montage.png" }
```

### 5.6 出手点 5：动画编排（阶段 ⑥，新增）

**背景**：v1 的六个预设是代码常量（`spine.ts:220-445`），只对标准人形名生效。参考项目同样是查表（`build_spine_json.py:166-473`）且**只有 rotate/translate 两条轨道**。

**v2 的三层结构**：

| 层 | 谁做 | 产出 |
|---|---|---|
| **L0 预设** | 脚本（免费、确定） | 按 §附录B 的参数表实例化成关键帧数据 |
| **L1 AI 编排** | AI | 「这个角色该做哪些动作、幅度基调是什么、要不要加武器挥砍」，输出**参数与覆写**，不是原始关键帧 |
| **L2 人工 K 帧** | 人 | 时间轴编辑器里改任意一帧（§6.6） |

**为什么 AI 不直接写关键帧**：AI 写关键帧的错误率极高（数值量大、需要角度直觉），而**参数化覆写**是低维的、可校验的、可回退的：

```jsonc
{ "actions": [
    { "preset": "walk", "params": { "duration": 0.9, "strideAmplitude": 1.2, "armCounterSwing": 1.0 },
      "reason": "这是个慢节奏的 NPC 走路" },
    { "preset": "attack", "params": { "weapon": "right-hand", "windup": 0.12, "strikeSpeed": "fast" },
      "reason": "右手持刀" } ],
  "add": [ { "name": "float", "duration": 2.0, "loop": true,
             "params": { "hipBob": 8, "armDrift": 12 }, "reason": "角色是水生，漂浮着" } ] }
```

**脚本必须自动校验的三条原则**（参考项目只写在 prose 里、脚本不校验，`SKILL.md:1941-1944`）：

1. **相关骨骼错开时间**（head 峰值晚于 torso ≈ 0.1s = follow-through）；
2. **大骨骼大动作**（`|Δhip| ≥ |Δtorso| ≥ |Δhead|`）；
3. **所有循环首尾值一致**（`loop: true` 时每条轨道首末帧值必须相等）。

第 3 条尤其重要：v1 与参考项目的循环接缝全靠人工约定。它是**纯本地、免费、可断言**的检查，必须做成硬校验。

**新增两条 v1 与参考项目都缺的能力**：

- **scale 轨道**（squash & stretch）：起跳/落地的 `scaleY` 挤压拉伸、打击的瞬时 scale 脉冲。注意 `translate/scale/shear` 的 bezier 是 **8 个数**（附录 A）。
- **Path 约束驱动的次级运动**：飘带/头发/尾巴。AI 只需给一条路径 + 摆动参数，运行时自动摆骨链（DragonBones `Constraint.ts:230-834` 的两档精度，自研可只实现弧长表那一档）。

### 5.7 出手点 6：结构体检与诊断（贯穿全程）

**v1 已有两道检查**（`riggen.ts:1486-1527`）：头在脚下面 → 结构不合理；均分 < 0.32 → 拆件图与参考图很可能不是同一个角色。

**v2 把它扩展成一份体检表**，每阶段结束都跑，结果进验收包：

| 检查 | 阶段 | 判定 | 动作 |
|---|---|---|---|
| 部件数 vs 网格格数 | ② | 缺格 ≥ 40% | 告警：模型很可能没按网格摆（v1 已有，`riggen.ts:1299-1307`） |
| 单件不透明占比 | ② | < 1% 或 > 98% | 标记该件需重生成 |
| 语义完整性 | ③ | 缺 `head`/`torso`/`hip` | 拒绝进入 ④ |
| 语义环 / 父级缺失 | ③ | 有环 | 拒绝写入 |
| 均分 | ④ | < 0.32 | 告警：角色可能被换过（v1 已有） |
| **垂直结构序** | ④ | head 中心 y > foot 中心 y | 告警（v1 已有） |
| **水平镜像约束** | ④ | left-* 与 right-* 同侧 | 自动纠正（v1 已有，`rigpose.ts:1732+`） |
| **遮挡一致性** | ④ | 前面部件的可见像素与参考图差异过大 | 建议重排 z 序 |
| 骨骼无环 | ⑤ | 有环 | 拒绝 |
| 动画循环接缝 | ⑥ | 首末帧值不等 | 拒绝或自动闭合 |
| 关键帧属性 vs bezier 长度 | ⑥ | `translate/scale/shear` 的 curve 长度 ∉ {8} | **拒绝导出**（附录 A 第 2 条） |
| 图集区域 vs slot | ⑧ | 有 slot 找不到区域 | **硬失败**（参考项目只打 WARNING，`generate_spine_player.py:68-75`） |
| 图集边界 | ⑧ | `x+w > atlasW` 或 `y+h > atlasH` | **硬失败**（参考项目会静默裁切，`make_atlas.py:32-53`） |

### 5.8 出手点 7：逐部件贴图重绘 / 换色 / 回退（阶段 ② 与 ⑦）

**这是 v2 从「一次成型」走向「可迭代」的关键**：某一块部件画得不好，不必重新生成整张拆件图，而是重绘那一块。

**★ 与 reskin-app 的根本差异**：reskin-app 把**整张 atlas 或整张合成图**丢给 Gemini 重绘，回来必须再用 SAM / 连通域 / IoU 模板**反向切回各个 slot**（`cc_segment.py:72-111`）。v2 是**逐部件重绘**——一个部件进、一个部件出——因此：

> **反向切分、SAM 服务、连通域 + IoU 匹配这一整套都不再需要**（§3.1 的范围裁剪带来的最大简化）。

抄它做得好的部分（这些与「是否要反向切分」无关，仍然成立）：

| 做法 | 采纳 | 理由 |
|---|---|---|
| **宽高比对齐 + 白底 padding + 1:1 裁回**（`gemini.py:207-232`、`:168-177`） | ★ **原样采纳** | 把「生成模型会改画幅」消灭在进入流水线之前，下游坐标数学才能直接复用。**最值得抄的一招** |
| **遮罩 = alpha 相乘 + 按尺寸分档腐蚀**（`atlas_rebake.py:320-345` + `settings.py:29-38`） | ★ **原样采纳** | 「AI 生成部件边缘一定有白晕」是普遍问题；形态学 close 补洞 + 分档 erode，且**细部件腐蚀半径更小**（默认 px `0/1/2/3`，阈值 `60/200/500`）以保住睫毛/描边 |
| **逐部件回退到原图**（`reverted_slots.json`） | ★ 采纳并推广 | 「这张 AI 头发不行，换回原版；其它保留」是真实需求。reskin-app 用一个小 JSON 记录，v2 做成**通用版本指针**（见下） |
| **同一批次共享风格参考图**（`gemini.py:155-159` 的 `reference_images` 顺序约定） | 采纳 | 逐部件重绘时，风格一致性靠「角色整图 + 已定稿的部件」作参考图来保证 |
| **没有真正的 mask-conditioned inpaint**（`server.py:614-624`） | ⚠️ **不采纳其名** | reskin-app 的「Retouch」实际是「整张 bbox 丢回去 + prompt 求保持轮廓 + **事后** alpha 裁剪」。v2 要么接真正的 inpaint，要么**在 UI 上如实叫「重绘这张贴图」**，不要叫「局部修补」 |
| **原地覆写 AI 输出**（`atlas_rebake.py:87-90` 的 `img.save(source)`） | ✗ 不采纳 | 重跑时输入已被改过，无法复现。v2 一律「写新版本文件 + 文档记录版本」 |
| **命名不一致**（rebake 写连字符 `server.py:529,557`、export 写下划线 `:886` / `atlas-{skin}` `:872`，而前端只探测连字符 `SpineCanvas.tsx:211-212`） | ✗ 明确避免 | 命名必须收敛到一个函数，多处共用。**这类 bug 是「同一个概念有两套命名」的必然结果** |
| **重打包恒写 `offset:0,0` + `orig == size`**（`atlas_repack.py:80-81`） | ✗ 明确避免 | 丢图集 trim 信息 → 区域中心 ≠ attachment 中心 → 部件偏移（`skin_writer.py:69-78` 的注释承认了这个问题，但只靠「保住默认 width/height」治标）。v2 必须落真实 `orig`/`offset`（§7.4） |

**v2 的统一模型**：每一次重绘都产出「一张贴图 + 一份 provenance」，**永不覆盖原图**：

```
parts/head.v1.png          ← 原始（v1 生图或用户上传）
parts/head.v2.png          ← AI 重绘（已过遮罩 / 宽高比对齐）
parts/head.v2.json         ← { provider, model, prompt, negative, mask, aspectRatio, padding,
                               source: "head.v1.png", at }        ← 可复现、可审计
parts/head.current         ← 指针（文本文件，内容是 v1 / v2 / …）
```

`RigDocument` 里的 `parts[n].activeTexture = "v2"` 即该指针；「回退原版」＝改一个字段。

**换色**（不调 AI、纯本地）抄 reskin-app 的 `imaging.py:93-141` 滑杆集合（Hue `-180..180` / Saturation `0..3` / Lightness `-1..1` / Brightness `-1..1` / Contrast `0..3` / RGB Balance `-0.5..0.5`），**但必须立即反映在画布上**——这正是 reskin-app 最大的 UX 缺口：它的滑杆只存在 zustand 内存里，**不改变 Pixi 画布上的角色渲染**，只在 export 时才烘焙（`App.tsx:67`）。v2 的换色是 `RigDocument` 上的一个字段，画布走同一个求值器（§8），天然实时。

### 5.9 已裁剪的出手点 8：导入外部骨架（不做）

**决策（§3.1）：不导入、不编辑其它工具产出的骨架。** 因此本节原本设计的「解析外部骨架 → AI 补语义 → 换装组识别」整个出手点**取消**，AI 出手点从 8 个收敛为 7 个。

两条仍然适用的教训（虽然场景变了，但它们是**所有**骨骼格式的共性约束，v2 自己写出的骨架同样会踩）：

- **timeline 全部按骨骼名/插槽名索引**，名字不一致会**静默不生效、不报错**。所以 v2 里「改骨骼名」必须同步重映射 `animations.*.bones` 的键（已列入 §11.2 A8 断言）。
- **`displayFrameCount` 与帧动画索引强耦合**（DragonBones `Slot._setDisplayIndex` 按**下标**索引）。v2 若启用多套贴图（§6.7 的可选部分），换贴图后必须校验每个 slot 的 display 列表长度与顺序。

**关于 reskin-app 的教训（仅作对照，不落地）**：它的 `parser.py` 对骨架的理解是**扁平的 slot→attachment 映射**（`_report_reskin_app.md` §3.1），**不解析**骨骼层级、变换、drawOrder、mesh、weights、约束；所以 `exploded_compose` 把 attachment 的 bone-local `(x,y)` 直接当世界中心，**忽略骨骼层级与旋转**（`exploded_compose.py:82-104`，代码注释自己承认 "This won't be a true rest pose because we ignore the bone hierarchy"）。这是「只做扁平映射」的必然代价——如果将来要重开导入路径，**必须解析完整骨架**，不能只抄它的扁平解析器。

### 5.10 提示词与上下文工程

v1 已经有一套成熟的对话工具体系（`tools.ts` 的 `game_material_intake` / `game_material_call` / `game_material_review` / `game_material_approve` + 固定流程 + 审核模式）。v2 的 AI 出手点**全部复用这套通道**，不新开体系。

补充两条：

1. **每个 AI 出手点都要在系统提示词里写清「输入是什么、输出 schema 是什么、边界在哪」**。参考项目把脚本原文内嵌进 SKILL.md（`build_skill.py:55-82`，实测 5/5 字节一致）以保证「模型看到的代码 = 人维护的代码」，但它的 prose 与代码**全面漂移**（`_report_spine_ai.md` §8.19：预设数字、jump 阶段数、`google-generativeai` 依赖名、homography vs similarity、10 parts vs 12 regions 全对不上）。
   → **v2 的教训**：把易漂移的事实（参数表、schema、阶段契约）**放进代码生成提示词**，不要重述在 prose 里。

## 6. 手工出手点（编辑器规格）

### 6.1 统一编辑模型：一切编辑 = 事务性 patch

**这是把「AI 与手工平等」落到工程上的机制。**

```ts
interface RigPatch {
  target: string;          // JSON 路径，如 "layout.items.head.x" / "skeleton.bones.torso.offset.rotation"
  value: unknown;
  op?: "set" | "add" | "remove" | "reorder";
  by: "human" | "ai";
  label: string;           // 展示用，如「拖动头部」
  evidence?: string;       // AI 必填：看过的图
}

interface PatchResult {
  revision: number;        // 单调递增，用于乐观并发
  invalidated: string[];   // 由 §4.4 计算
  undoToken: string;
}
```

**四条规则**：

1. **UI 与 AI 走同一个 `applyPatch`**。不存在「UI 有特权通道」——这是 reskin-app 两套变换语义冲突（§2.2）的直接对治。
2. **一批操作 = 一个事务**。拖动一次、撤销一次、AI 的一次响应，各算一个事务。v1 已经理解这一点（`riggen.ts:1607-1616` 注释解释了为什么 `saveRigLayoutItems` 是批量的：逐条提交会「读盘 + 改 + 落盘 + 重出合成图」一条几百毫秒，连续微调会明显卡顿）。
3. **本地草稿 + 乐观提交**。v1 的装配台做对了：拖动时只改 CSS，不等宿主回图；松手才提交一次（README:402-403）。v2 把这一模式推广到骨骼与时间轴。
4. **每个 patch 带 `by`**。`provenance` 就是它的累积产物，直接对应 `adjustment-format.md` 的 `{original, user, final}` 三元组（`:28-46`），并支持它要求的「零位移也记录」＝「这块人看过」（`:48-60`）。

### 6.3 骨骼编辑器（阶段 ⑤，新增）

**这是 v2 相对 v1 最大的能力增量之一。**

| 操作 | 交互 | 落到文档 |
|---|---|---|
| 选中骨骼 | 点画布上的骨骼线 / 点骨骼树 | 高亮 |
| 平移骨骼原点 | 拖骨骼根部圆点 | `skeleton.bones[n].offset.x/y` |

| 改父子关系 | 骨骼树上拖拽重挂 | `bones[n].parent` + **重映射动画键**（§4.4） |

### 6.5 蒙皮与权重编辑器（阶段 ⑤c，新增，可选）

**优先级低于 6.3/6.6**，但对「裙摆/披风/长发」这类需要软变形的部件是必需。

| 层级 | 能力 | 复杂度 |
|---|---|---|
| **L0 自动绑定**（免费） | 按几何距离给每顶点分配 1-3 根骨骼的权重 | 中 |
| **L1 网格生成** | 对部件包围盒做自适应三角化（或用户手画网格） | 中 |
| **L2 顶点权重编辑** | 选中顶点 → 调权重 → 热力图显示 | 高 |
| **L3 FFD 编辑** | 在时间轴上对某帧拖顶点，形成 deform 关键帧 | 高 |

### 6.6 时间轴与关键帧编辑器（阶段 ⑥，新增）

**这是「动画是数据」这一决策的直接兑现，也是 v1 最被用户诟病的缺失。**

| 能力 | 规格 |
|---|---|
| 轨道列表 | 按骨骼分组，每根骨骼下 `rotate / translate / scale / skew` 四条轨；另加 slot 轨（`color / display`）与 ffd 轨 |

| **缓动曲线编辑** | 可视化 bezier 手柄。**注意语义**：控制点是**绝对量**（时间/值空间），且**每个被动画属性一份**（`rotate` 4 个数、`translate/scale/shear` 8 个数）；curve 属于「以该帧为**起点**」的段 → 末帧永不携带 curve（附录 A） |

**关键的工程取舍**：v1 的编辑器与播放器都在宿主半区生成 HTML（`rigpreview.ts`）。v2 的时间轴编辑器必须是**客户端 React 组件**（因为要交互），所以 §8 的求值器必须能在浏览器里跑（经典脚本约束：无 `import`/`export`，全部用 `React.createElement`，README:678-679）。

### 7.2 Spine 4.2 导出的四条地雷（必须写成校验器）

来源：`spine-animation-ai/scripts/build_spine_json.py:92-153`（docstring 原文）+ `references/spine-json-spec.md:53-81`。已核实 `:125-153` 的转换代码。

| # | 地雷 | 写错的后果 | 校验 |
|---|---|---|---|
| 1 | 旋转值写 `value` 不是 `angle` | 4.x 运行时把 `angle` 读成 0 → **什么都不转** | 导出前断言：所有 rotate 时间轴不含 `angle` 键 |
| 2 | bezier **每个被动画属性一份**：`rotate` 4 个数、`translate/scale/shear` **8 个数** | 只给 4 个 → 运行时越界读 undefined → NaN 沿骨骼变换扩散 → **渲染一帧后整体消失** | 断言：`curve.length ∈ {4, 8}`，且与时间轴属性数匹配 |
| 3 | 控制点是**绝对量**（`cx` 是时间、`cy` 是值，单位同相邻关键帧），不是 0..1 | 归一化会让手柄落到自己所在区间之外 → 插值**突跳**而不是缓动 | 断言：`curve[0] ∈ [t_i, t_{i+1}]`，`curve[2] ∈ [t_i, t_{i+1}]` |
| 4 | keyframe 的 curve 属于**以它为起点**的段 | 简写第 i 帧的曲线实际描述 `i-1 → i`；**末帧永不携带 curve** | 断言：每条时间轴的末帧无 `curve` 键 |

绝对化的正确公式（`build_spine_json.py:146-153`）：

```
cx1 = t1 + (t2 - t1) * cx1_norm      cy1 = v1 + (v2 - v1) * cy1_norm
cx2 = t1 + (t2 - t1) * cx2_norm      cy2 = v1 + (v2 - v1) * cy2_norm
```

**并且仓库里已经有一对现成的回归夹具**（`_report_spine_ai.md` §8.11）：

- **坏样例**：`examples/sombrero/skeleton.json:4` 声明 `"spine": "4.2.0"`，但正文是 3.8 写法——`"angle": 0`（`:279`）、translate 的 curve 只有 4 个数（`:312-317`）。**正好命中地雷 1 与 2。**
- **好样例**：`examples/sombrero/sombrero.json:4` 是 `"spine": "4.2"`，用 `"value"`（`:299`）+ 8 个数的 translate curve（`:272-281`，`[0.25,0,0.75,0, 0.25,0,0.75,3]` 恰等于 `_convert_timeline` 的绝对化结果）。

→ **这两份文件应直接搬进 v2 的测试夹具目录**，断言校验器能分别判「坏」与「好」。

### 7.3 DragonBones 5.5 导出（新增）

| `skeleton.bones[]` | `armature[0].bone[]` | **`transform:{x,y,skX,skY,scX,scY}`**；`skY`=rotation（度），`skX`=绝对斜切角；**建议强制 `skX === skY`** 以免引入双角度复杂度 |
| `bones[n].parent` | `bone[].parent` | 解析器会缓存后补，允许父级出现在子级之后（`ObjectDataParser.ts:334-357`），但建议拓扑序输出 |
| `bones[n].length` | `bone[].length` | 会乘 `armature.scale` |
| `bones[n].inherit.*` | `bone[].inheritTranslation/Rotation/Scale/Reflection` | 默认全 true |
| `skeleton.slots[]` | `armature[0].slot[]` | 数组序即 `zOrder`；`color` 用 `{aM,rM,gM,bM,aO,rO,gO,bO}`（×100 的整数） |
| `skeleton.slots[].blendMode` | `slot[].blendMode` | 字符串或枚举数字均可 |
| `skins[]` | `armature[0].skin[]` | `[{name, slot:[{name, display:[…]}]}]`；空名字规范成 `"default"` |
| region attachment | `display:{type:"image", name, path, pivot:{x,y}, transform}` | **`pivot` 归一化，默认 `0.5/0.5`，且不在图集里** |
| `meshes[]` | `display:{type:"mesh", vertices, uvs, triangles, weights, slotPose, bonePose, inheritDeform, width, height}` | 见 §7.5 |
| `constraints[]` (ik) | `armature[0].ik[]` | `{name, bone, target, bendPositive, chain, weight}` |
| `constraints[]` (path) | `armature[0].path[]` | `{name, target, bones[], positionMode, spacingMode, rotateMode, position, spacing, rotateOffset, rotateMix, translateMix}` |
| `animations[]` | `armature[0].animation[]` | `duration` 是**帧数**（不是秒）：`duration = seconds * frameRate` |
| `animations[].bones.<name>.rotate` | `animation[].bone[].rotateFrame[]` | 帧字段 `{duration, tweenEasing, rotate, skew, curve?}` |
| `animations[].bones.<name>.translate` | `translateFrame[]` | `{duration, tweenEasing, x, y, curve?}` |
| `animations[].bones.<name>.scale` | `scaleFrame[]` | `{duration, tweenEasing, x, y, curve?}` |
| `animations[].slots.<name>.color` | `animation[].slot[].colorFrame[]` | 帧字段 `value: {aM:…}` |
| `animations[].slots.<name>.display` | `animation[].slot[].displayFrame[]` | **Step，不插值** |
| `animations[].ffd` | `animation[].ffd[]` | `{name, skin, slot, frame[]}` |
| `animations[].events` | `animation[].frame[]` | `{duration, events:[{name, bone, slot, ints, floats, strings}]}` |
| `animations[].blend` | `animation[].blendType / fadeInTime / playTimes` | `blendType: "none" \| "1d"` |
| `atlas` | 独立 `_tex.json` | `{name, imagePath, width, height, scale, SubTexture[]}` |

#### ⚠️ DragonBones 特有的三个坑

1. **`tweenEasing` 缺省 = 阶跃**（`-2` = `TweenType.None`，`ObjectDataParser.ts:1462-1489`），不是线性。导出时**每个补间帧都要显式写 `tweenEasing: 0`**（或真实缓动值），否则动画会一跳一跳。
2. **`curve` 的长度有奇偶约定**（`ObjectDataParser.ts:147-221`）：长度 `%3 == 1`（= 6n-2，如 4）是紧凑式（首锚 `(0,0)`、末锚 `(1,1)` 省略）；否则是显式锚点式。**注意**：DragonBones 的 curve 是 **0..1 归一化**的，而 Spine 4.2 是**绝对量**——同一份 `RigDocument` 的两条导出路径必须用**不同的** curve 编码器。
3. **`duration` 单位不同**：Spine 是秒，DragonBones 是帧数。转换时用文档里的 `fps`（建议固定 30，与 `frameRate` 一致）。

### 7.4 图集导出

| 格式 | 文本结构 |
|---|---|
| **Spine `.atlas`** | 首行 png 名 → `size: w,h` / `format: RGBA8888` / `filter: Linear,Linear` / `repeat: none` → 每区域：名字、`  rotate: false`、`  xy: x, y`、`  size: w, h`、`  orig: w, h`、`  offset: 0, 0`、`  index: -1`（缩进两空格） |
| **DragonBones `_tex.json`** | `{name, imagePath, width, height, scale, SubTexture:[{name, x, y, width, height, rotated, frameX, frameY, frameWidth, frameHeight}]}` |

**装箱算法**：v1 的 `packAtlas`（`spine.ts:823-850`）与参考项目的 `make_atlas.py:32-53` 是同一个策略——**按高度降序的货架装箱**，`padding=2`，尺寸取 `nextPow2`，且**结果可复现**（同样的输入永远得到同样的坐标，用户重跑不会因为坐标漂移而误以为产物变了，`spine.ts:816-822` 的注释讲了这个理由）。**这个策略在十几个部件的量级上足够好，保留。**

**但必须修掉参考项目的两个缺陷**（否则 v2 会继承 bug）：

1. **超宽件无扩宽分支**（`make_atlas.py:32-53`）：若某件宽度 + 2×padding > `atlasW`，代码只是换行，然后在 `rx=padding` 处照放不误，`Image.paste` **静默裁掉超出部分**，而 `.atlas` 里仍写完整的 `size` → **区域与像素不符，运行时画出错位图**。
   → 修法：`atlasW = max(nextPow2(estimate), nextPow2(maxPartWidth + 2*padding))`，并在 blit 后**断言** `x + w <= atlasW && y + h <= atlasH`。
2. **恒写 `orig == size` 且 `offset: 0,0`**（`make_atlas.py:88-93`、`atlas_repack.py:80-81`）：永远不裁透明边、永远不记录 trim offset。这在「闭环自洽」时能跑（reskin-app 靠「保住默认皮肤的 width/height」绕过，`skin_writer.py:69-78`），但代价是**原始图集的 trim/offset 信息永久丢失**，且导出的图集比必要的大得多。
   → 修法：v2 的图集**落真实的 `orig`（未裁剪尺寸）与 `offset`（裁剪偏移）**，并把 attachment 的 `x/y` 按裁剪中心偏移修正。

**新增的硬校验**（参考项目只打 WARNING，`generate_spine_player.py:68-75`）：

- 每个 slot 引用的 attachment 名在图集里必须存在；
- 每个区域的 `x+w ≤ atlasW`、`y+h ≤ atlasH`；
- 区域数量 == 参与导出的部件数量；
- 检测多页需求：若 `atlasH > 4096`（可配置上限），输出多页并同步写 `.atlas` 的多 page 段（v1 与参考项目都不支持分页，`atlas_reader.py:37-38` docstring 明说「只读第一页」）。

### 7.5 自包含预览 HTML 的升级

v1 的 `rigpreview.ts:41-392` 已经是**正确的方向**：部件图与骨架 JSON 全部 base64 内联、自带 Canvas 渲染器（含贝塞尔插值、骨骼叠加、时间轴），零外部依赖。

## 8. 运行时与渲染器规格

### 8.1 为什么必须自己写

三个参考源给的答案分别是：

- `spine-animation-ai`：`generate_spine_player.py` **根本不渲染**，只把数据 base64 塞进 `rawDataURIs` 调 UNPKG CDN 的官方播放器（`:160-161`），并在 `:288` 自认「requires internet for the Spine Player CDN」——却在 docstring `:4-6`、`SKILL.md:1959-1961`、`README.md:164` 三处宣称 standalone。
- `reskin-app`：依赖 `@esotericsoftware/spine-pixi-v8`（`package.json:12`），**需要一个浏览器运行时 + Pixi**，且它自己的应用代码完全不处理 mesh/权重/deform（`_report_reskin_app.md` §5.6：`applyTransforms` 调的 `updateRegion()` 是 RegionAttachment 的方法，对有 `typeof` 守卫——**mesh attachment 拖拽改了属性但不生效**）。
- `DragonBonesJS`：需要 Pixi（`dragonBones.min.js` 231KB + pixi）。

**v2 的约束决定了必须自研**：

1. **验收页可能在无外网环境打开**（v1 已经为此拒绝了官方 Spine Web Player，README:428-432）——排除 CDN。
2. **客户端半区是经典脚本**（无 `import`/`export`，所有 React 元素用 `React.createElement`，README:678-679）——把 Pixi 内联进 `client.js`（当前已 274KB）不现实。
3. **宿主侧要离线渲染合成图/对比图/验收图**（v1 的 `renderLayoutImages`，`riggen.ts:1714-1753`）——那里根本没有浏览器。
4. **编辑器需要「拖动骨骼时部件实时跟随」**（§6.3）——需要求值器可被 React 组件直接调用，而不是隔着 iframe。

**所以：自研一个求值器（L6），同时供宿主（Node，离屏渲染）与客户端（浏览器，实时预览）使用。**

### 8.2 求值链规格

```
1. 取动画当前时间 t
   ├─ 若多动画混合：按 layer 降序分配权重（BlendState 算法）
   ├─ 每条轨道按 frameIndices（每帧→关键帧下标表）O(1) 定位当前段
   └─ 插值：Line / Curve(bezier) / QuadIn / QuadOut / QuadInOut / stepped
        → 输出 animationPose（每骨骼一个 Transform）

2. local = origin ⊕ offset ⊕ animationPose        ← 三通道（§4.5）
   ⊕：x/y/rotation/skew 相加；scaleX/scaleY 相乘

3. 沿骨骼树自顶向下：world = parentWorld ∘ local
   ├─ 若 inheritScale=false：位置用父矩阵转，角度直接相加，自身缩放不进矩阵
   │   （DragonBones Bone.ts:239-299 —— 防「父级非均匀缩放把子级拉成斜切」）
   └─ 若父级是 Surface：取 Surface 的分片仿射矩阵（按顶点所在格子）

4. 约束求解（在 Bone.update 的等价时机）
   ├─ 排序：target 必须排在 root 之前（拓扑）
   ├─ IK：chain=1 → 两骨余弦定理（h=(lPP-lLL+lTT)/(2lTT)、r=√(lPP-h²lTT)/lT），
   │       膝盖取两支由 (det(parentMatrix) < 0) !== bendPositive 决定；weight<1 即软 IK
   └─ Path：按 positionMode/spacingMode/rotateMode 求每根骨的目标点与切向，
            translateMix/rotateMix 做强度插值

5. slot 显示
   ├─ displayIndex 时间轴（step，不插值）决定当前 display
   ├─ color 时间轴：8 通道（aM,rM,gM,bM,aO,rO,gO,bO）
   │   注意 DragonBones 的做法是「对目标值指数逼近」：
   │   result += (target - result) * pow(fadeProgress, 4)   ← 支持过渡中再次改目标
   └─ 计算 pivot 像素化：rect = frame ?? region；rotated 且无 frame 时交换 w/h；
      再 += frame.x/y × scale（DragonBones Slot.ts:410-452）

6. mesh 变形（若有）
   ├─ 无权重：x = vertex*scale (+deform)
   └─ 有权重（LBS）：for 每个顶点，for 每根影响骨骼：
        xG += (M · (xL, yL) + t) * weight        M = 骨当前世界矩阵
        （deform 位移加在骨骼局部坐标上）
      → 抄 DragonBones PixiSlot.ts:265-350

7. 绘制
   └─ 按 slot 顺序（= z 序）；attachment 原点 = 图片中心：
        translate(boneWorld) → rotate(boneWorldRot) → translate(att.x, att.y)
        → rotate(att.rotation) → scale(1,-1) → drawImage(-w/2, -h/2, w, h)
      （v1 的 rigpreview.ts:272-279 已经是这个序列，正确）
```

### 8.3 性能规格

| 场景 | 要求 | 手段 |
|---|---|---|
| 客户端拖动骨骼 | ≥ 30fps（含 mesh） | 只重算被改骨骼的子树（脏标记）；`meshes` 只在必要时重算 |
| 客户端播放动画 | ≥ 60fps（≤ 40 骨骼，无 mesh） | `frameIndices` O(1) 定位；只在关键帧下标变化时重插值 |
| 客户端播放动画 | ≥ 30fps（含 mesh 与 FFD） | `cacheFrameRate`：每骨骼每帧缓存 10 个 float（a,b,c,d,tx,ty,rotation,skew,scaleX,scaleY），命中则整块跳过矩阵运算与 `fromMatrix` 反算（`atan/atan2` 是热点） |
| 宿主批量渲染 | 16 部件合成图 < 300ms | 保留 v1 的解码缓存（按「路径 + mtime + 大小」缓存，`riggen.ts:1692-1712`）+ 求值器可复用的骨骼世界矩阵 |
| 宿主导出图集 | 4096² < 1s | 行式装箱 + 直接 blit（`blitOpaque`，`riggen.ts:1996-2002`） |

### 8.4 与宿主半区的分工

| 渲染任务 | 在哪 | 为什么 |
|---|---|---|
| 实时预览（编辑器画布） | 客户端 | 要交互、要跟手 |
| 装配合成图 / 对比图 | 宿主 | 产物要落盘供 AI 与人工验收 |
| 部件蒙太奇 | 宿主 | 同上（v1 已有，`riggen.ts:1240-1286`） |
| 带标签的 bbox 图 | 宿主 | 抄 `position_parts.py:377-391` 的 `name [method] s=scale m=matches` 标注 |
| 图集 | 宿主 | 要写 PNG |
| 自包含预览 HTML | 宿主生成，浏览器打开 | 零依赖验收（v1 已有） |

**要求**：求值器核心（步骤 1-6）必须是**同一份代码**，宿主与客户端共用。因为客户端是经典脚本，实现方式是——用 TypeScript 写一份 `src/rigruntime.ts`，构建时同时产出：
- `lib/rigruntime.js`（宿主 ESM 模块）；
- 内联进 `lib/client.js` 的 IIFE 片段（构建脚本处理，类似现有的 `strip-client-export.mjs`）。

  共同输入，所以「编辑」这个动作不需要任何格式转换——只是把参数化的预设**固化**成显式关键帧。
- **语义**：`saveRigAnimation` 不传 `animation` 就是**实例化**（把当前参数烘进关键帧）。
  一旦实例化，这台动画就以数据为准，`animationSettings` 的旋钮不再影响它——刻意的：
  否则手调过的帧会被下一次调参悄悄改掉。
- **校验**：写盘前过 `normalizeCustomAnimation`——时间非负、逐轨道时间严格递增、
  重合帧去重、每条轨道首帧必须是 0、末帧 curve 强制清空、curve 只接受 4 个数或 `"stepped"`。
  丢掉的东西一定伴随一条 warning，不做静默修正。
- **界面**：`RigTimelineEditor`——动画 tab（标「已改」）、时长/循环开关、逐轨道关键帧条
  （百分比定位，点选/拖动/双击加帧）、选中帧的时间与数值输入、六个缓动预设、
  加/删轨道（rotate/translate/scale）、「还原到预设」、改完自动重算预览。
  **拖动只改本地草稿、松手才提交**（与装配台一致）。
- **预览联动**：iframe 的 `src` 带 `?v=${rig.updatedAt}`。少了它 React 认为 src 没变、
  不重新挂载，改完关键帧预览会一直是旧的。
- **scale 轨道**：新增在 `TimelinePropertyCount` 已有的 `scale` 上（本就是双属性、8 个控制点），
  编辑器可以加/删，导出两条路径都已支持。

#### 顺手修掉的两个真 bug

1. **末帧携带永不生效的 `curve`**。`kf()` 给每帧都挂了默认缓动，而 Spine 的 curve 描述的是
   「以本帧为起点」的下一段——末帧没有下一段，`convertTimeline` 用的是 `authored[i+1]`，
   所以末帧那个 curve 永远不会被读到（附录 A 第 4 条）。导出不受影响，但**编辑器**里
   用户会看到一个永远改不动的字段。现在 `instantiateAnimation` 强制清空。
2. **`invalidateFrom` 不清空「自己」那一阶段**。原实现 `if (from < index) 置空 else 只清 approved`，
   于是 `setRigBoneOffsets` / `saveRigAnimation` / `renameRigPart` 这些传 `"rig"` 的入口
   只清掉了「通过」标记，`rig.status` 仍是 `ready`——界面继续显示「已完成」，
   用户以为改动已经生效了（实测：改完 walk 的关键帧后 `rig.status` 还是 `ready`）。
   现在按阶段分开处理：**`layout` 保留 `items`**（那是用户手工摆的劳动成果，
   不能因为「改了一个先验」就被抹掉），**`rig`/`atlas` 置空**（纯派生物，重跑就有）。
3. **单击关键帧就会改时间**。拖动逻辑没有「手抖阈值」，`mousedown` 之后任何一次
   `mousemove`（哪怕 0 位移）都会按鼠标位置重算时间——实测点一下 `walk` 里 0.6s 的帧，
   它当场变成 0.401s。用户只是想选中它改数值，位置先跑了。现在位移小于 4px 不算拖动。
4. **相邻关键帧会塌缩成 0 帧**。两帧相隔不足 1/30 秒时会落在同一个 `frameStart` 上，
   中间那帧的 DragonBones `duration` 就是 0（被解析成阶跃），**导出前校验直接拦下整条骨骼链路**。
   现在保存时把时间对齐到 30fps 网格并合并同帧的关键帧，坏数据根本进不了任务。
5. **快照没暴露 `rig.updatedAt`**。客户端拿它给预览 iframe 做缓存破除（`?v=`），
   少了它 React 认为 src 没变、不重新挂载，**改完关键帧预览一直是旧的**——
   「改了没反应」里最难查的一种：数据全对，只是没人让浏览器重新去拉。

#### 还有一个「界面不同步」的竞态

`run()` 里的 `tasks.active` 在 `await fn()` 返回时就变回 false，而 `kick()` 是
「登记后台任务后立即返回」——宿主写 `running` 落盘、以及本地任务（推骨骼 / 装配 /
打图集，通常不到 1 秒）跑完，都发生在这一次 `load()` **之后**。于是 `busy` 一直是 false、
轮询不启动，界面停在旧状态：**表现为「点完按钮没反应、下一步的按钮还是灰的」**，
用户只能手动刷新页面（实测踩过：骨骼明明建好了，③ 还是没打勾）。
修法是提交成功后开一个 6 秒的「沉降窗口」保持轮询。

#### 已完成（含实测记录）

- **DragonBones 5.5**：`src/rigexport.ts` 的 `buildDragonBonesSkeleton` / `buildDragonBonesTexture`，
  `src/rigvalidate.ts` 的 `validateDragonBones` / `validateDragonBonesTexture`。落盘位置

  资源路由白名单加了 `export`。
- **同一个 `RigDocument` 两份写法的分岔点只有三处**，都逐行对着 DragonBonesJS 的解析器核过：
  1. `tweenEasing` **缺省是 `-2`（阶跃）**，所以每个补间帧都得显式写 `0` 或真实缓动；
  2. `curve` 是 **0~1 归一化**（紧凑式要求长度 `% 3 === 1`），而 Spine 是绝对量——
     因此简写动画被拆成 `buildAnimationShorthands`（两条路径共同的输入），各自编码一次；
  3. `duration` 是**帧数**（`seconds × frameRate`，取 30）。
- **图片落点靠 `pivot` + `frame*`**，不在 display 的 `transform` 里独立表达：
  运行时算的是 `_pivotX = pivot.x * frameWidth + frameX`（`armature/Slot.ts:409-461`），
  所以 `pivot = 0.5/0.5` + `frameX = 裁剪偏移`（负值）才能让**原图中心**落回挂点上。
  裁剪过的部件少给 `frame*` 会整体偏掉，校验器把「只给一半」判成 error。
- **坐标是 y 向下**（`DragonBones.yDown` 默认 `true`），与我们的图像坐标一致，旋转角不取反。

#### ★ 顺手修掉的一个自 v1 起就存在的静默 bug

DragonBones 的拓扑序校验一上来就拦住了真实任务：

```
armature/…/hip 父级「torso」不存在或出现在子级之后
```

根因不在导出器，而在**骨骼推导**：`resolveParent(name, seen)` 把「按名字找父级」和
「按祖先栈断环」揉在一起，然后被**调用两次**（拓扑排序传祖先栈、写骨骼字段传空集），
两次结果可以不同；更糟的是断环之后的兜底「挂到 torso」把刚断开的边**又接了回来**
且不再复检。默认 16 部件网格里 `hip` 的语义父级就是 `undefined`（身体根），
于是每一次导出都产出 `hip ← torso` + `torso ← hip` 的**互环**，而且**一条告警都没有**。

修法：
1. 拆出 `rawParentOf`（只管语义与关键词）+ `resolvedParent`（父级只解析一次，
   排序与产物共用同一份），两者不可能再分叉；
2. 兜底宿主**只服务默认网格之外的部件**——已知槽位走到兜底只有 `hip` 一种情况，
   而它本来就是根；
3. `validateSpineWire` 也加上骨骼拓扑序断言，同一个 `RigDocument` 的两种写法不能只拦一边。

回归测试在 `verify-rig.mjs` 第 12/13 节（成环语义 + 默认网格），
以及 `verify-rig-module.mjs` 里对真实流程产物的断言。

#### 已完成：IK 约束（验收判据的第一条）

- **数据**：`job.constraints[]`（`{name, bone, target, chain, bendPositive, weight}`）。
  内部用 DragonBones 的写法（末端骨 + 链长），因为导出时 Spine 要「从根到末端的骨骼名数组」、
  DragonBones 要「末端骨 + chain」，后者更好反推。
- **目标骨自动补**：目标骨不在骨架里时 `buildSkeleton` 补一根无贴图、无长度的点，
  位置取链末端的**骨尖**（绑定姿势）——加上约束的那一刻姿态不跳，用户看到的是一个可直接拖的点。
- **求值器**（`rigpreview.ts`）：`updateWorld → solveIk → updateWorld`。
  先算未约束的姿态（软 IK 的插值起点），求解，再让结果生效。`weight<1` 按最短角差插值。
- **拖动**：预览页里直接拖那个青色菱形。拖动值走 `dragX/dragY` 覆盖动画值——
  拖动是用户的即时意图，不该被动画轨道盖掉。另加只读验收钩子 `window.__gmmPreview`
  （`bones()` / `iks()` / `tip()` / `screen()`），否则「手跟随」只能靠肉眼看截图。
- **导出**：Spine 写 `ik: [{name, bones:[…], target, mix, bendPositive, compress, stretch, uniform}]`；
  DragonBones 写 `armature.ik: [{name, bone, target, chain, bendPositive, weight}]`。
- **校验**：链引用、目标存在、目标不在链上（自环）、末端骨有长度、`mix` 在 0~1。

#### 两处踩过的几何坑（都写进了注释）

1. **链上的骨骼不一定首尾相接**。IK 的经典推导假设「子骨原点 = 父骨骨尖」，
   而我们的骨骼原点取的是**部件近端锚点**——实测举起的右臂两段被摆在同一小块区域，
   实际间距 41.9px 而上臂长度 140px。用 `parent.length` 当第一段长度，会解出
   「当前姿态已经对齐」而骨尖离目标 241px。改成用**实际距离**。
2. **子骨的朝向要相对父骨朝向算**（`父骨朝向 + (π − b)`），不能相对 `base`——
   P1 并不在 P0→target 的直线上，两者差一个 `a`。写错这一项的表现是
   「IK 看起来转了、骨尖就是不到目标」，实测差 91°。

真机验证（Playwright）：拖动前目标与骨尖都在 `(148, 585)`、gap=0；
把目标拖到 `(267.17, 679.18)` 后骨尖**同样**是 `(267.17, 679.18)`、gap=0——
「拖动目标点时手跟随」精确成立。

### M8 · 拆件质检（方案外新增，起因是一次真实踩坑）

这一节不在原方案里。它是**被真实数据逼出来的**：用一张真实的蓝发女仆立绘跑完整条链路时，
生成 18 个部件、界面显示「部件（18）——逐件验收」一切正常，装配却把「头」摆到了「大腿」下面。
逐块看图之后发现三件事同时成立：

1. **同一个部位被画进了多个网格格子**——4 段「大腿→膝盖」、4 只「鞋袜脚」、3 条「整袖」。
   实际只有 12 块是真实部位（参考图里可见的独立部位本来就只有 14 块左右）。
2. **网格位置决定部件名，模型却按自己的理解画**——第 2 格叫「胯部」画的是裙子、
   第 9 格叫「脖子」画的是大腿、`left-lower-arm` 画的是膝盖。而骨架是拿「名字 → 语义」
   这条链推的，**名字错了，骨架从第一根骨头起就是错的**（与匹不匹配准无关）。
3. **部件是重新绘制的**，与参考图像素不像，模板匹配只能挑一个「不那么错」的位置：
   相似度 0.08~0.50，而界面照样显示「已定位 17/18」。

三种都不是「报错」，而是「看起来成功了」。所以要有一步把它们变成**明确的、可读的结论**。

#### 判据

| 检查 | 手段 | 判定 |
|---|---|---|
| **重复件** | 裁到内容包围盒 → 归一化 64×64 alpha 轮廓 → 两两 IoU | 同向 IoU ≥ 0.86 并组报 error |
| **左右件 vs 重复件** | 同上，但把 B 水平翻转后再比一次 | 镜像 IoU 明显高于同向 → 是左右各一，**不并组** |
| **对称形状** | 同向与镜像 IoU 都很高 | 无法区分 → 降级为 warning，让人确认（判错会缺一整条肢体） |
| **装配质量** | 平均/最低相似度、低于 0.5 / 0.3 的个数 | 均值 < 0.5 报 error，并给出「先给先验再重跑」的具体命令 |
| **部件数超标** | 与「参考图目测约几个独立部位」比较 | 超出报 error。这项**只能靠视觉**，所以留成参数由人/agent 填，给不出就不判断 |

实测判别能力（真实部件、直接量出来的）：

| 配对 | 同向 | 镜像 | 结论 |
|---|---|---|---|
| `right-upper-leg / left-lower-arm` | **0.975** | 0.745 | 同向 → 真重复 |
| `left-upper-leg / neck` | **0.934** | 0.713 | 同向 → 真重复 |
| `right-upper-arm / left-upper-arm` | **0.901** | 0.145 | 同向 → 真重复 |
| `right-upper-leg / left-upper-leg` | 0.761 | **0.961** | 镜像 → 左右件 |
| `right-foot / left-foot` | 0.663 | **0.952** | 镜像 → 左右件 |

#### 落地

- `src/rigqa.ts`：`findDuplicateParts` / `assessParts`（纯计算，不碰文件系统）。
- **分割后自动跑**（那一次部件像素已在内存里，不必再解盘），结果写进 `job.qa`；
  **装配后更新**相似度部分（重复件结果复用，因为这里没有像素）；
  `runRigQa({jobId, expectedParts?})` 可手动重跑。
- 界面面板 `RigQaPanel` 放在**所有阶段之前**：它同时管「拆件可不可信」与「装配准不准」，
  而这两件事分属①②两个阶段，塞进任一个里都会让另一处看不到。面板里直接给出结论、逐条建议、
  「重新质检」与「参考图里大约几个部位」输入。
- 对话侧：`renderStatus` / `renderReview` 都输出结论与建议，`rigNextActions` 在质检不通过时
  **把质检建议排在所有阶段建议之前**——不然 agent 会在错误素材上继续往下做功。

#### 拆件提示词的三种硬约束（用真实数据换来的）

拿真实立绘连跑两轮拆件之后，提示词里补上了三条**原来没有、但代价很大**的约束：

1. **每个部位只画一次**（`every cell shows a DIFFERENT part`）。
   模型会为了填满网格把同一个部位画进多个格子——实测 4 段「大腿→膝盖」、4 只鞋袜脚、3 条整袖，
   18 块里只有 12 块是真实部位。多出来的部件会被硬塞进不相干的骨骼位。
2. **格子的名字就是该画什么的依据**（`draw what the cell says`，并在每格后面附上明确的
   英文部位描述）。网格位置决定部件名，而骨架是拿「名字 → 语义」推的——
   实测标着 `hip` 的格子画出了裙子、标着 `neck` 的格子画出了大腿，**骨架从第一根骨头起就是错的**。
   所以 `RIG_SLOTS` 里每个槽位加了 `en` 字段，提示词写成 `hip = hip / pelvis (...)`。
3. **左右成对的部件必须是镜像，不是复制**（`MIRRORED, not copies`）。
   实测两条「左右袖」同向重合 0.901（应该是镜像），装配时怎么摆都不对。

还有一条是**从错到对**的：第一版写的是「按解剖结构补全被衣服遮住的部位」，
结果模型把 `hip` 画成了**短裤**（参考图里那处是裙子），外观与参考图不符、模板匹配全废。
改成 **`CUT, do not redesign`**（格子名只决定切哪块，外观一律照参考图）之后，
`hip` 恢复成「裙子 + 围裙 + 鲸鱼尾」、`neck` 变成参考图里真正的荷叶边领子。

两轮对比：

| | 第一版（按解剖重画） | 第二版（照参考图切） |
|---|---|---|
| 质检 | 100% 通过（16 块无重复） | 100% 通过（16 块无重复） |
| `hip` | 短裤（参考图里没有） | **裙子 + 围裙 + 鲸鱼尾** |
| `neck` | 一个小圆环 | **荷叶边领子** |
| 画风 | 标准解剖件 | 与参考图一致 |

**顺带确认了一件事**：拆件质量与自动装配质量是两件事。即使拆件完全正确
（16 块、命名对、左右镜像、画风一致），**模板匹配对「服装裁片」仍然失手**——
因为裁片只覆盖参考图里的一小块，而匹配要求整块相似。拆件图里匹配得好的全是
「封闭、独特、无遮挡」的件（领子 0.66、上衣 0.67、袖子 0.63~0.72、鞋 0.60），
头和腿这些「与身体连成一片」的件只有 0.10~0.28。这是方法的边界，不是 bug——
所以 README 里那句「自动摆位只是起点」是字面意思。

#### 顺带修掉的一个数据一致性问题

手工摆过位置的部件仍带着**旧的匹配分数**（`score` 描述的是自动匹配的质量），
于是质检会拿一个陈旧数字当「这次装配准不准」的证据——实测手工摆对之后它仍然报
「平均相似度 0.326，不可信」。现在 `saveRigLayoutItems` 会清掉 `score`/`coverage`，
`runRigQa` 也会跳过 `manual === true` 的项（双保险）。

### M7 · 体验与性能

**已完成（装配台视图）**

- **zoom/pan**：滚轮以光标为锚缩放（`Ctrl/Cmd+滚轮` 同键位；`Ctrl/Cmd+0` 适应窗口），

**顺手修掉的两个真 bug**（都是 Playwright 实测撞出来的，编译期完全看不出来）：

1. `setHistory([])` 挂在 `[job.id, job.updatedAt]` 上。`commit()` 自己就会写盘并改
   `updatedAt`，于是**每提交一次就清空撤销栈**——「撤销」按钮永远是灰的，`Ctrl+Z` 也永远
   没反应。拆成两个 effect：历史栈只跟 `job.id`，草稿跟 `updatedAt`。
2. `undo()` 把从历史栈弹出的**改动前**快照也塞进重做栈，重做时还原的还是那一份
   ——点重做等于又撤一次，表现为重做按钮毫无反应。改成先把「当前状态」抓进重做栈。

### 12.1 高风险

| # | 风险 | 影响 | 缓解 |

| R1 | **`RigDocument` 迁移会让老任务失效** | 用户已有的 rig 任务打不开 | M0 先做迁移器 + 保留 `job.json` 不删 + 迁移失败时回落到 v1 只读视图 |

| # | 问题 | 选项 | 建议 |

### 12.3 已决策：外部骨架导入路径裁剪

**决策**：**不做外部工具产出骨架的导入与编辑**；**保留**本插件历史任务（v1 `job.json`）的迁移。

| 维度 | 结论 |
|---|---|
| 路径 A / B（生图拆件 / 上传部件） | **做**（主链） |
| 路径 M（本插件 v1 任务迁移） | **做**（M0 的迁移器，`job.json` 保留不删以便回滚） |
| 路径 C（外部 Spine / DragonBones 骨架导入换皮） | **不做** |

**这个裁剪消除了三类工作量**（原方案里它们占了相当大的比重）：

1. **图集反向切分**（explode）与 **skin 写回**——原本需要「解析 .atlas → 按 region 切出单图 → 重打包 → 写回 `skins[]`」的完整闭环，以及配套的 trim/offset 保真问题（reskin-app 正是在这里丢了 `orig`/`offset`，`atlas_repack.py:80-81`）。
2. **外部骨架的完整 schema 解析**——原本要兼容 Spine 的 list/dict 两种 skins 形态、legacy `bounds:` atlas、多页图集、DragonBones 的 `skX/skY` 双角度模型、`weights` 的两种方言、`dbbin` 等。现在只需解析**自己写出的**文件，且只为自己校验。
3. **语义对齐**——给无语义的 `slot_17/slot_18` 起名、识别换装组。这类问题在路径 A/B 里不存在：部件名从生图阶段的网格或用户上传的文件名就已经确定。

**收益**：`skins[]` 从「核心阶段」降级为「数据结构保留、编辑器不暴露」；AI 出手点从 8 个收敛为 7 个；M6 从「多皮肤 + 外部骨架导入」变成单一的重绘闭环。

**保留的可逆性**：`RigDocument` 与 §8 的求值器在设计上已经覆盖了外部骨架的绝大部分结构（骨骼层级、mesh/权重、约束、多皮肤在 schema 里都有位置）。若将来要重开导入路径，缺的是「语义对齐」与「图集 explode/重打包」两个模块，而不是重写求值器或数据模型。

**唯一需要注意的遗留问题**：v1 的历史任务里，`parts` 与 `layout` 的数据结构在 v2 里有变化（新增 `role`/`parent`/`proximal`/`distal`、`provenance`、`offset`）。迁移器必须为这些新字段给出**确定的默认值**，且默认值应当**复现 v1 的行为**（即：用 v1 的 `RIG_SLOTS` 表填 `role/parent/锚点`，`provenance.origin` 填 v1 的 layout 值，`offset` 全零）——这样迁移后的任务导出结果与迁移前一致，用户不会看到「打开老任务骨架变了」。

## 附录 A · Spine 4.2 四条地雷速查

来源：`spine-animation-ai/scripts/build_spine_json.py:92-153`（已核实 `:125-153`）+ `references/spine-json-spec.md:53-81`。

| # | 规则 | 写错的表现 |
|---|---|---|
| 1 | 旋转值在 `value` 下，**不是** `angle`（`angle` 是 3.8 写法） | 4.x 运行时读成 0 → **骨骼什么都不转** |
| 2 | bezier **每个被动画属性一份**：`rotate` 4 个数；`translate` / `scale` / `shear` **8 个数**（x、y 各 4 个） | 只给 4 个 → 运行时读过数组末尾读 undefined → NaN 沿骨骼变换扩散 → **渲染一帧后骨架整体消失** |
| 3 | 控制点是**绝对量**（`cx` 是时间、`cy` 是值，单位同相邻关键帧），不是 0..1 | 手柄落到自己所在区间之外 → 插值**突跳**而不是缓动 |
| 4 | keyframe 的 curve 属于**以它为起点**的那一段 → 简写挂第 i 帧的曲线实际描述 `i-1 → i`，**末帧永不携带 curve** | 时间轴错位一帧；末帧多带一个会被忽略的 curve |

绝对化公式：

```
cx1 = t1 + (t2 - t1) * cx1_norm      cy1 = v1 + (v2 - v1) * cy1_norm
cx2 = t1 + (t2 - t1) * cx2_norm      cy2 = v1 + (v2 - v1) * cy2_norm
```

标准 ease 的归一化控制点：`[0.25, 0, 0.75, 1]`；EaseIn `[0.42, 0, 1, 1]`；EaseOut `[0, 0, 0.58, 1]`；EaseFast `[0.4, 0, 0.2, 1]`。

**现成的回归夹具**（直接从参考项目搬）：

- 坏：`examples/sombrero/skeleton.json`（声明 4.2.0，正文用 `angle`:279 且 translate curve 只有 4 个数:312-317）
- 好：`examples/sombrero/sombrero.json`（`value`:299 + 8 个数的 translate curve:272-281）

## 结语

v1 用最少的代码把「一张图 → 可用骨架」跑通了，并且已经在**阶段化、局部重跑、视觉先验、自包含预览**四件事上超过了它的参考项目。v2 不应该推倒这些，而应该补上它缺的那一块：**让「数据」而不是「流程」成为 AI 与人的共同工作面**。

具体就是三句话：

1. **一份文档**（`RigDocument`）替代「一串产物」——AI 读它、人改它、导出用它。
2. **三个通道**（`origin` / `offset` / `animationPose`）让 AI 的重跑与人的修正不再互相覆盖。
3. **九段流水线**让每一次修改都只付它该付的代价。

参考项目 `spine-animation-ai` 把「Spine 4.2 的四个地雷」和「遮挡投票定序」这两件事做对了，把「定位→构建」的接口留成了空白；`reskin-app` 把「AI 重绘 + 遮罩回贴」的流程做通了，但因为没有作业模型、因为两套变换语义冲突，把「可迭代」这件事丢了；`DragonBonesJS` 则给出了这套系统能达到的表达力上限——**它的 `Bone.offset` 三通道模型与 `curve` 控制点设计，是本方案里最值得直接照搬的两样东西**。
